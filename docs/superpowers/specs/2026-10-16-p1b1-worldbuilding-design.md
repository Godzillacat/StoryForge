## 1. 阶段定义

### 1.1 在路线图中的位置

`CLAUDE.md` §7 的 P1b「世界观」按 §4.4 有六件事：设定条目、人物、关系网、时间线、术语表、规则硬度（**状态推进**依赖章节，随 P1c 走）。六件事一次做完约 15–17 个任务，**比 P1a（13 个）还大**，而 P1a 的教训是切片越大、真实问题暴露得越晚。故拆为两段：

| 切片 | 内容 | 状态 |
|---|---|---|
| **P1b-1 设定与规则** | 设定条目 + 规则硬度 + 术语表 + 世界观智能体 | 本文档 |
| P1b-2 人物与关系 | 人物（含称呼表）+ 关系网 + 时间线 | 后续 |

拆分的依据不是「哪一半更简单」，而是**同构性**：设定条目、规则、术语是同一形状的实体，共用一套容器与关联机制；人物有十个字段、关系网是双向边、时间线是有序事件，三者结构各不相同。

### 1.2 验收标准

作者能完成以下全流程，且全程可编辑、可回退、AI 产出不被当作成品：

1. 从解析卡与故事圣经出发，**一次运行**得到一批设定条目候选（类型、标准写法、别名、概述、描述、规则类的硬度）；
2. 候选**逐条**审：采纳 / 改后采纳 / 丢弃；同名候选被预先标出；
3. 不经过 AI **手工**新建、编辑、删除条目；
4. 给条目加**别名**与**标签**；
5. 在两条条目之间建立**有向关联**并说明是什么关系；
6. 给规则类条目标注**硬度**（硬 / 软 / 氛围）；
7. 在**术语表**里按字面形式查到任一标准写法与其别名，以及来源条目；
8. 在调试台看到这次候选生成的渲染后完整提示词、原始返回、token、耗时、花费。

### 1.3 明确不做

- 人物、关系网、时间线（P1b-2）。
- **SQLite FTS5 全文检索** —— 放在 P1b-2 之后。理由：FTS5 的意义是让上下文组装器的「相关设定条目（检索）」槽位有源可取，而那个源正是设定条目；有了本切片与 P1b-2 的真实语料，检索才可测（能断言「搜『记忆交易』返回那三条」）。另有一处真未知：FTS5 默认分词器 `unicode61` 把整串中文当作一个词，需靠 `trigram` 或入库前分词解决 —— 那是一个要先探的可行性问题，不该塞进本切片。
- **数据迁移框架** —— 放在 P1b-1 与 P1b-2 之间做一个薄切片。本切片只**新建**两张表，`create_all` 够用；P1b-2 几乎必然要给 `setting_entry` 加字段（人物那十个字段若走同一张表），届时没有迁移框架就只能删库重建。
- 锁定（D-03 的「可锁定」在路线上属 P4）、影响面分析、快照与分支、伏笔账本。
- 关系图可视化（D-19：一期用表格）。
- 正文层的一切（生成、润色、一致性审计、逻辑自检）。

## 2. 数据模型

只建本阶段真正写入的两张表，一律带 `id` / `created_at` / `updated_at`（沿用 `db/base.py` 的 mixin）。

### 2.1 `setting_entry`

| 字段 | 类型 | 说明 |
|---|---|---|
| `project_id` | FK → `project`，CASCADE | |
| `type` | String(30)，索引 | 英文键，见下表 |
| `name` | String(200) | 标准写法 |
| `aliases_json` | JSON list[str] | 别名 / 称呼方式 |
| `tags_json` | JSON list[str] | 标签 |
| `summary` | Text | 一句话概述。列表视图与日后注入上下文用它，避免整段描述挤占预算 |
| `description` | Text | Markdown 正文 |
| `hardness` | String(20)，可空 | `hard` / `soft` / `atmosphere`，**仅 `rule` 有值** |
| `source_run_id` | String(36)，可空 | 从哪次运行采纳来（D-03 可追溯）。手工新建的为 null |

**唯一约束**：`(project_id, name)`。同一项目里两个同名条目就是一处真实的不一致，不该被允许。

**type 取值与中文名**：

| key | 中文 | 出处 |
|---|---|---|
| `place` | 地理 | §4.4 |
| `faction` | 势力 | §4.4 |
| `organization` | 组织 | §4.4 |
| `rule` | 规则体系 | §4.4 + D-11 |
| `event` | 历史事件 | §4.4 |
| `item` | 物品 | §4.4 |
| `concept` | 概念 | §4.4 |
| `term` | 术语 | §4.4 |

中文名由接口下发（`GET /api/entry-types`），前端不硬编第二份 —— 与 `SLOT_REGISTRY` 同一条教训。

### 2.2 `entry_relation`

| 字段 | 类型 | 说明 |
|---|---|---|
| `project_id` | FK → `project`，CASCADE | |
| `from_id` | FK → `setting_entry`，CASCADE | 起点 |
| `to_id` | FK → `setting_entry`，CASCADE | 终点 |
| `kind` | String(60) | 关系名，如「位于」「下属」「敌对」。自由文本，不做枚举 |
| `note` | Text | 补充说明 |

**有向**。`kind` 是自由文本而非枚举：P1b-2 的关系网会复用这张表（人物之间的边，两端都是人物类条目），而人物关系的词表（师徒 / 血缘 / 挚友…）与本层的（位于 / 下属 / 敌对…）不该用同一个枚举。

**为 P1b-2 预留的形状**：关系网额外需要「强度」。本切片**不建**该字段（YAGNI），但它是一个可空列，P1b-2 加上去时本表已存在的行不受影响。

### 2.3 刻意不建的东西

- **不建草稿态。** 候选条目留在 `generation_run.parsed_json` 里，只有采纳才写 `setting_entry`。内容三级（D-04）因此不需要在表上再表达一遍 —— 与 P1a 采纳架构同构。代价：丢弃的候选只存在于运行记录里，要回看得去调试台翻。
- **不建锁定字段。** 属 P4。
- **不建术语表独立的表。** 见 §3.3。

## 3. 功能设计

### 3.1 世界观智能体

预置阵容新增一张角色卡（P1a 的运行时原样复用，不新造机制）：

| 项 | 值 |
|---|---|
| `key` | `worldbuilder` |
| 名称 / 定位 | 世界观构建师 / 设定 |
| `task_type` | `worldbuilding`（`roster.py` 的 `TASK_TYPES` 已登记） |
| `trigger_mode` | `assist`（协同档；D-06 的三档在此体现为「AI 出候选、作者逐条审」） |
| 上下文槽位 | `parsed_idea`、`story_bible`、`project_core` |
| 输出契约 | 见下 |

**刻意不放 `tool_library`**：那 25 份模板讲结构、人物弧光与节奏，不含世界观构建法；放进去只挤占预算。

**输出契约**（每个属性带中文 `title`，P1a 的契约说明块机制直接吃）：

```
{
  "entries": [
    { "type", "name", "aliases": [str], "summary", "description", "hardness" }
  ],
  "open_questions": [str]
}
```

- `entries` 必填、至少 3 项；`type` 用 §2.1 的英文键，用 `enum` 约束。
- `hardness` 只在 `type == "rule"` 时有意义，其余为空；**不在 schema 上做条件约束**（自写的校验子集不支持），改为在提示词里说明、由校验器容忍。
- 提示词沿用解析师那套纪律：引用解析卡与故事圣经里的**具体要素**说明为什么需要这条设定；**不许编造设定填空**，没把握的写进 `open_questions`；不替作者决定故事的走向。

### 3.2 候选链路

**一次运行 = 一批候选**（本切片的核心取舍）。

```
点「让 AI 提候选」→ RuntimeService.execute(worldbuilder)
  → 候选落在 generation_run.parsed_json
  → 前端渲染候选列表
  → 作者逐条：采纳 / 改后采纳 / 丢弃
  → 采纳走 POST，写 setting_entry 并记 source_run_id
```

- **改后采纳**：作者在行内改字段再点采纳，提交的是**改后的值**（与 P1a 采纳故事圣经同一条承诺）。
- **重名**：渲染候选时前端拿已加载的条目列表**预先比对**，同名候选标「已存在」并默认置为丢弃。这样不需要一个「冲突确认」接口，作者也不会点下去之后才被告知失败。后端仍以 `(project_id, name)` 唯一约束兜底，冲突时返回可读中文原因。
- **别名冲突**只在界面**提示**、不阻断 —— 别名共用是合法的。
- 已知代价：候选一次性出现，作者要等整批生成完（本仓实测重模型单次可到 180 秒）。界面上明示进度，不靠改传输层解决（流式仍按 P1a 收口的决定留给 P2）。

### 3.3 术语表

**不单独建数据。** 术语是「专有名词的标准写法」，而每个条目都有名字与别名 —— 它们天然就是术语。

`GET /api/projects/{id}/terms` 返回一个**投影**：所有条目的 `name` ∪ `aliases` 展平为行，每行带来源条目 id 与类型；`type == "term"` 的裸术语（只有名字、没有完整设定，如虚构的计量单位）本身也是行。

用途：作者查标准写法的单页；也是 P2 的「正文出现表外新词时提醒」将要查的那份白名单。

### 3.4 三档介入在本层的落法

| 档 | 本切片的落法 |
|---|---|
| 手动 | 新建 / 编辑 / 删除条目完全不经过 AI，与 AI 候选走同一张表与同一套接口。**必须真实可用**（P1a 的教训：L1 手动档当初无路可走） |
| 协同（默认） | §3.2 的候选链路 |
| 自动 | 不做。它意味着 AI 连续推进、遇检查点才停，属 P3 的管线编排 |

沿用 P1a 的「协作模式」密度（左树 + 右控制面板），不引入沉浸模式。

## 5. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/entry-types` | 类型清单（key + 中文名），唯一真相在后端 |
| `GET` | `/api/projects/{id}/entries` | 条目列表，可按 `type` 过滤 |
| `POST` | `/api/projects/{id}/entries` | 新建（手工或采纳候选；采纳时带 `source_run_id`） |
| `PATCH` | `/api/entries/{entry_id}` | 编辑 |
| `DELETE` | `/api/entries/{entry_id}` | 删除 |
| `GET` | `/api/projects/{id}/relations` | 关联列表 |
| `POST` | `/api/projects/{id}/relations` | 建立关联 |
| `DELETE` | `/api/relations/{relation_id}` | 删除关联 |
| `POST` | `/api/projects/{id}/entries/suggest` | 跑世界观智能体，返回 `{run, entries, open_questions, structured, parse_error, raw_text}`（与 P1a 的架构推荐接口同形） |
| `GET` | `/api/projects/{id}/terms` | 术语投影 |

分层硬约束照旧：`api` 只做参数校验与调用 `services`；`services` 不碰 HTTP；候选生成走 `RuntimeService`，不新增运行时逻辑。

## 6. 测试策略

纯逻辑必须测（pytest），UI 不写自动化测试。

| 层 | 测什么 |
|---|---|
| 模型与 CRUD | 新建 / 编辑 / 删除 / 按 type 过滤；`(project_id, name)` 唯一约束真的会拒绝重名；`source_run_id` 写入与读回 |
| 关联 | 建立 / 删除；级联（删条目时其关联一并消失）；有向性（A→B 不等于 B→A） |
| 术语投影 | 展平结果 = 全部名字 ∪ 全部别名 ∪ 裸术语；每行带来源条目；空项目返回空列表 |
| 候选生成 | 用假传输层跑一次 `suggest`：结构化时返回候选、未结构化时返回原文与原因、无服务商时给可读中文原因 |
| **契约一致性** | 复用 P1a 已建的护栏 —— `test_contract_block_covers_every_field_of_every_preset_agent` 与 `test_preset_prompts_do_not_hand_list_field_keys` **自动覆盖新阵容**，前提是新角色卡进 `DEFAULT_ROSTER`。另加：`type` 的 `enum` 与 §2.1 的键表一致 |
| 类型清单 | `GET /api/entry-types` 的键集合与角色卡契约里的 `enum` 一致（防止两处漂移） |

前端：`pnpm build` 干净 + 浏览器走查。

**真实模型验证**：本切片完成后跑一次「提候选 → 逐条采纳 → 查术语表」，确认候选质量可用且不出现「未结构化」。消耗额度，做之前报预算。
