## 1. 阶段定义

### 1.1 为什么切出这一段

上位文档的 P1b-2 装了三件事：**人物（含称呼表）、关系网、时间线**。它们在**结构上各不相同** —— 人物是「一种条目 + 八个专属字段」，关系网是有向边，时间线是有序事件。这与 P1b 当初被拆成 P1b-1 / P1b-2 时用的理由是同一条（「设定条目 / 规则 / 术语是同构的三项，人物、关系网、时间线结构各不相同」）。

拆分的**分界线不是大小，而是「依赖不依赖模型」**：

- **本段（人物）**要扩世界观构建师的输出契约 —— 必须尽早拿真实模型验证它出的人物能不能用；
- **下一段（关系网 + 时间线）**是纯手工维护的功能，不依赖模型，即使拖后也不会卡住验证。

而 P1a 的教训原话是「切片越大真实验证越晚」，所以把「要验模型的」单独切出来先做。

**另外，这一段是迁移框架的第一次真正使用。** 上一个切片交付的 `run_migrations` / 备份 / 分派三条路径，截至目前 **`MIGRATIONS` 一直是空的** —— 框架的改表路径从未真正执行过。本段是它的第一次实战。

### 1.2 验收标准

1. **存量库启动** → 迁移执行一次、`setting_entry` 多出八列，**原有设定条目一条不少、已有字段值不变**；再启动一次**不重复执行**。
2. 手工新建一个人物（类型 = 人物），姓名、称呼与八项字段**落库读回一致**。
3. 把一个人物**改成「势力」** → 八项字段**保留**；而把一条规则改成势力 → `hardness` **仍被清空**（既有行为不变，两个行为各有测试钉住）。
4. **术语表投影里出现该人物的姓名与每一条称呼**。
5. **世界观构建师一次运行 → 候选里可以出现人物候选**，八项字段被填；采纳后按验收 2 的方式落库。
6. 角色卡契约里人物的**八个可选属性齐全**（键集合与 `CHARACTER_FIELDS` 一致，由测试钉住）。
7. **前端**：世界观页出现「人物」一组；编辑器按当前类型显示对应字段；术语表页可按类型筛选。
8. 既有测试**全绿**（当前基线 232 条）。

### 1.3 明确不做

- **逐章状态推进**（人物状态按章节记录）—— 章节要到 P1c 才有，那时才有地方挂；而「当前状态」作为一个字段本段就做。
- **弧光类型枚举化 / 归一化** —— 见 §5.3。
- **人物头像、关系图** —— 关系图是二期（D-19）。
- **关系网与时间线** —— 本切片第二段。

## 2. 数据模型

### 2.1 八列

给 `setting_entry` 加八列，**全部可空 Text、默认 NULL**：

| 契约键 | 列名 | 界面标签 | 形态 |
|---|---|---|---|
| `appearance` | `appearance` | 外貌 | 多行文本 |
| `personality` | `personality` | 性格 | 多行文本 |
| `desire` | `desire` | 欲望 | 多行文本 |
| `fear` | `fear` | 恐惧 | 多行文本 |
| `arc_type` | `arc_type` | 弧光类型 | 单行文本 |
| `abilities` | `abilities` | 能力边界 | 多行文本 |
| `speech_style` | `speech_style` | 说话风格样本 | 多行文本 |
| `current_state` | `current_state` | 当前状态 | 多行文本 |

上位文档 §4.4 列的十项里，「姓名」命中已有的 `name`，「全部称呼方式」命中已有的 `aliases_json`（其契约标题**本来就写作「别名与称呼」**），其余八项即上表。

### 2.2 为什么是显式列而不是 JSON

上位文档 §7.3 的草图用的是 `entity.fields_json`。本设计**偏离**这一点，理由与既有先例一致：

- 这八项是产品**明确列举的固定字段**，不是为容纳未知类型而设的通用容器 —— 它们不会「自由扩展」；
- 「按弧光类型筛选」「按当前状态筛选」是有意义的查询，JSON 查询要退化到 `json_extract` 且索引麻烦；
- 前端编辑器需要稳定字段，不必按 schema 动态渲染；
- **先例**：`hardness` 已经是一个「只对某一类条目有值的类型专属可空列」。本设计把它从「一个」推广到「一类」。

代价如实记下：`setting_entry` 会因此出现九个只对某一类条目有值的列（`hardness` 属规则、其余属人物），这张表越来越像几种实体的并集。**若日后类型专属字段继续增长**（比如势力、地点各自长出五六个专属字段），应当停下来重新考虑「拆表」或「JSON 块」，而不是继续加列。本条记入变更记录。

### 2.3 类型改了不清空（刻意偏离 `hardness`）

`hardness` 在条目类型改成非规则时会被**清空**，理由是「留着会让界面显示一个不存在的概念」。本设计**不**把这套规则扩到人物八项：

- 八项是作者手写的长文本，误点一次类型就静默丢掉太重；
- 保留的代价是表里可能留下「非人物条目带着人物字段」的隐形数据 —— 但它不会显示、不影响任何检查，且类型改回来内容还在（**可恢复**比**干净**更值钱）。

两个行为都要有测试钉住，且本条记入变更记录。

### 2.4 术语表与称呼表是同一份投影

`list_terms` 已是「条目名字 ∪ 别名」的投影。称呼并进 `aliases_json` 后，**称呼表无需新建任何结构** —— 它就是这份投影里 `type == "character"` 的那些行。

这一点是刻意的：P2 的「正文出现表外新词时提醒」查的白名单，与作者在界面上看到的称呼表，**是同一份数据**。

**顺带把一条已知事项的影响说清。** P1b-1 的账本留过一句给 P2 的注意事项：同一 `form` 可以来自两个条目，而投影不做歧义标记，「P2 建白名单查找表时须规定『同一 form 可多行，取值优先 is_primary』，否则会静默丢行」。**加入人物与称呼后，重名与重称呼的概率显著上升**（两个人物都可能被叫「老师」）。本段**不改**投影的这条行为 —— 但把它的紧迫度从「可能出现」提升到「几乎必然出现」，P2 建查找表时不能再放过。

## 3. 唯一真相：`CHARACTER_FIELDS`

八个字段的键名与中文标签会出现在：模型列、`_FIELD_TO_COLUMN`、`EntryCreate`/`EntryUpdate`、序列化输出、**角色卡契约**、**提示词**、**前端编辑器**。

P1b-1 吃过「契约与提示词各抄一份字段清单、漂移了没人发现」的亏，所以本设计按项目已有的两条先例收口 —— `SLOT_REGISTRY` 与 `ENTRY_TYPES` 都是「定义一次、其余处投影」：

- 在 `app/world_types.py` 定义**一次** `CHARACTER_FIELDS`（键 → 中文标签，八项，保持在 `ENTRY_TYPES` 旁）；
- **契约**里人物的八个可选属性**从它生成**；
- `_FIELD_TO_COLUMN` 从它派生八条 `{k: k}`（列名等于键名）；
- `/api/entry-types` **下发**它，前端按它渲染 —— 这个接口本就为「前端不硬编第二份清单」而建；
- **提示词里一个字段名都不写** —— P1a 收口时建的机制是「渲染层从 `output_schema` 自动注入字段说明块」，所以提示词只说人话。

结果：这八个键**只定义一次**。

### 3.1 前端为何不硬编

「前端直接硬编八个字段」更直白，选投影的理由是：**后端加了列而前端没跟上时，作者会编辑不到那个字段，且没有任何东西会报错**。经 `/api/entry-types` 下发，加字段只需改后端一处。代价是多一层「按配置渲染」的间接 —— 这是可接受的。

## 4. 迁移

**一条迁移，八条 `ALTER TABLE setting_entry ADD COLUMN`**，手写有序 SQL，版本号 1（`MIGRATIONS` 自建好以来第一次非空）。

- **只加可空列**，不重建表：SQLite 的 `ALTER TABLE ADD COLUMN` 对可空列是原地操作，作者的存量数据不受影响，也不触发 SQLite 改列类型所需的 12 步重建。
- **执行前自动备份**会真实触发一次（这是框架设计里「仅在真有步骤要执行时备份」那条规则的首次生效）。
- **全新库不走这条迁移**：它由当前模型直接建出（已含八列），被盖章为最新版本。两条路径的判据仍是「库里有没有业务表」。
- 迁移失败即拒绝启动（既有行为，本段不改）。

## 5. 契约与提示词

### 5.1 人物不新建候选种类

人物**就是 `entries` 里的一类 `type`**，不新开 `characters` 数组。理由：候选链路（一次运行出 3–8 条、逐条采纳 / 改后采纳 / 丢弃、采纳才入库、来源可追溯）与边界上的类型归一化**全部现成**，人物多开一条并行链路只会多一份要维护的一致性 —— 而那正是 P1b-1 吃过亏的地方。

契约的 `entries` item 增加八个**可选**属性（中文标题，从 `CHARACTER_FIELDS` 生成）。非人物候选不填；契约校验器刚放过的「可选字段为 null」正好兜住这类省略。

`ENTRY_TYPES` 增加 `character` → 人物，`_TYPE_TITLE` 随之为九类，契约说明块与前端下拉自动跟上。

**类型归一化不用改。** 模型返回中文「人物」时，既有的 `normalize_type` 会把它归到 `character` —— 因为归一化查的就是 `ENTRY_TYPES` 这份词表。这是「唯一真相」第一次在**新增一类**上自动生效，不需要动归一化函数本身。

### 5.2 提示词加的一节

- 人物**只在材料支持时给**，不为了凑数编造；
- 给了人物，就要把**适用于这个人物的**八项写满（不适用的可省）；
- 人物的「全部称呼方式」写进别名那一项；
- 没把握的进 `open_questions`（沿用既有的「不编」）。

### 5.3 弧光类型用自由文本

不枚举、不归一化。理由：它不参与任何**确定性检查**；强行收敛成词表就得像 `type` / `hardness` 那样再写一套归一化，收益却低。提示词里给几个常见类型（成长 / 堕落 / 平弧 / 幻灭 / 救赎）作参考即可。**等 P4 的逻辑自检真要拿它比对时再收敛** —— 那时它才有了成为词表的理由。

## 6. 服务层与 API

全部落在既有的接线点上，每个都不大：

| 位置 | 改动 |
|---|---|
| `app/db/models/world.py` | `SettingEntry` 加八列 |
| `app/world_types.py` | 加 `character` 到 `ENTRY_TYPES`；新增 `CHARACTER_FIELDS` |
| `app/services/world_service.py` | `_FIELD_TO_COLUMN` 从 `CHARACTER_FIELDS` 派生八条 |
| `app/api/schemas.py` | `EntryCreate` / `EntryUpdate` 各加八个可选字段 |
| `app/api/_serializers.py` | 条目输出加八个键 |
| `app/api/world.py` | `/entry-types` 增加「类型专属字段」一段 |
| `app/agents/roster.py` | 契约从 `CHARACTER_FIELDS` 生成人物属性；提示词加 §5.2 那一节 |

**类型改非人物时的清空逻辑保持只作用于 `hardness`**（见 §2.3）。

## 7. 前端

- **编辑器按类型渲染**：通用字段（类型 / 标准写法 / 别名与称呼 / 标签 / 一句话概述 / 详细说明）常显；类型专属字段按当前类型渲染 —— `rule` 出硬度（现有行为），`character` 出八项。八项由 `/api/entry-types` 下发的清单驱动，不硬编。`EntryEditor` 若因此过长，按项目约定拆出组件文件。
- **世界观页的树零改动** —— 它按 `type` 分组，多一类就多一组。
- **候选列表零改动** —— 人物候选混在同一份候选里，行上的类型标记显示「人物」（既有机制）。
- **术语表页加类型筛选**（全部 / 各类 / 人物），筛出人物即称呼表。这是通用能力，对其余八类同样有用。
- 前端不写自动化测试（项目约定），另出手工走查清单。

## 8. 测试策略

纯逻辑必须测（pytest），UI 不写自动化测试。

| 层 | 测什么 |
|---|---|
| `world_types.py` | `CHARACTER_FIELDS` 的键集合与契约生成的人物属性键集合一致；`ENTRY_TYPES` 含人物 |
| 契约 | 人物八个属性齐全且均为可选（不含在 `required` 里） |
| 迁移 | 一条迁移八条语句；在**存量库**（先按旧结构建表并写入数据）上执行后八列存在、原数据不丢；重复启动不重复执行 |
| 服务层 | 八字段落库读回一致；类型改非人物 → 八项**保留**；规则改势力 → `hardness` **清空** |
| 术语投影 | 人物的姓名与每一条称呼都在投影里，且 `type` 正确 |
| API | `/entry-types` 下发类型专属字段；`EntryCreate`/`Update` 接受八字段 |
| 跨产物一致性 | P1b-1 那条「查所有 ASCII 标识符 − 槽位 − 白名单」的护栏扩展覆盖人物字段 —— 契约加了字段而别处没跟时要能变红 |
| 回归 | 既有 232 条全绿 |

**真实模型复验**：跑一次世界观构建师，确认候选里能出人物且八项填得住、不编造、没把握的进 `open_questions`。**这会用掉阿里云百炼免费额度**（记忆里有这条约定：调用前先确认模型在额度内）。
