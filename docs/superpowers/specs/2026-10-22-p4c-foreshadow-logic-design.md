# StoryForge P4c 设计：伏笔闭环与逻辑链文本视图

> 2026-10-22。P4 的最后一段（P4a 锁定与影响面、P4b 快照与分支已完成）。产品 §4.11 要求版本与分支（已交付），§4.5 的伏笔账本在 P1c-2 已有只读视图；本段补两件 P4 完成标志里剩下的事：**伏笔账本闭环**与**逻辑自检深化（文本视图）**。

## 1. 阶段定义

### 1.1 这一段要解决什么

**问题一：伏笔只有「规划状态」，没有「走到哪一步」。** 今天的 `foreshadow.status` 复用的是章节状态词表（`planned` / `confirmed`），而 `actual_pay_scene_id` 只记「在哪一场被兑现」。作者想问的三件事它答不了：这条伏笔是**已埋未收**、**已收**、还是**作者决定不收了**？账本上「未回收」这一类把所有没实际回收的都算成一类，包括作者已经决定弃掉的那些。

**问题二：逻辑自检只有问题清单，没有「逻辑链」本身。** 产品 §4.6 说一期给「问题清单与逻辑链文本视图」（D-22 明确图形化放二期）。今天作者拿到十二条因果链问题，但看不到**这一场的因果链长什么样** —— 他得自己在正文里拼。

P4c 交付两件事：

1. **伏笔生命周期**：`planted`（已埋）/ `paid`（已收）/ `dropped`（作者决定不收）/ `planned`（规划中）四态，与「在哪一场」三个位置字段各自独立；回收率按它算，账本按它筛。
2. **逻辑链文本视图**：从已采纳正文里**按段落抽取**因果链与信息流，中性地列出「因为 → 所以 → 但是」，不做评判、不给建议（那是问题清单的事）。

### 1.2 验收标准

1. **伏笔生命周期**
   - `foreshadow.status` 的取值扩为 `planned` / `planted` / `paid` / `dropped`，词表与章节状态**分开**（章节只有 planned / confirmed，两者语义不同）。
   - **状态可从位置字段派生，也可显式设置**：显式 `dropped` 原样保留（作者的判断，位置字段不改它）；其余情况 `actual_pay_scene_id` 非空 → 视作 `paid`；显式 `paid` / `planted` 原样保留；`planned` 且埋设位置非空 → 视作 `planted`。
   - 账本增加「已收 / 已埋未收 / 已弃 / 未安排」四类计数；`dropped` 不计入「未回收」。
   - 回收率 = `paid` /（`paid` + `planted` + `planned`），`dropped` 不进分母。
2. **逻辑链文本视图**
   - 给定一个场景，从已采纳正文按段落抽取出**因果 / 转折 / 信息揭示**三类句子，按原文顺序列出，每句带段落序号。
   - **纯规则、不调用模型**：靠连接词与句式（因为 / 所以 / 于是 / 但是 / 然而 / 原来 / 才发现 等）识别，识别不到就老实说「这一段没有明显的因果连接」。
   - 视图与逻辑自检的问题清单并列展示，但**不混在一起**：链是「正文里写了什么」，问题是「哪里讲不通」。
3. **基线**：后端既有 889 条全绿；前端 30 条全绿、`pnpm build` 干净。
4. **本段不调用模型**。

### 1.3 明确不做

- **逻辑自检图形化视图**（因果链图、设定投放曲线、性格漂移曲线）—— 依 **D-22** 推到二期。本段只做文本视图。
- **逻辑链的语义理解** —— 规则识别连接词，不理解句子。理解是问题清单（LLM 层）的事，两者分工不同。
- **伏笔的自动状态推进** —— 正文写入时**不自动**把伏笔标成 `paid`（那要靠回写助手 + 作者确认，已有）。本段只做「派生显示」与「显式状态」。
- **伏笔删除 / 合并** —— 已有删除；合并两条伏笔是另一套语义。
- **回收率的历史曲线** —— 只有当前值。

## 2. 已定决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 状态词表 | **新建 `FORESHADOW_STATUSES`**，不复用 `chapter_types` | 章节的 `confirmed` 与伏笔的 `paid` 是两种语义；复用会让「已确认的伏笔」与「已回收的伏笔」被同一个值表示 |
| 派生 vs 显式 | **位置字段（事实）优先于状态（判断），只有显式 `dropped` 例外** | 位置字段是事实、状态是判断。作者说「这条我不收了」，埋设位置还在不该把它翻回 `planted` —— 那是唯一让判断压过事实的地方。反过来，作者早先标过 `planted`、之后回写助手经他确认记下了实际回收，若还显示「已埋」，同一行里状态列与「实际回收位置」列会互相打架，所以事实应当赢 |
| `dropped` 是否进回收率分母 | **不进** | 作者放弃的伏笔不该拉低回收率 |
| 逻辑链的抽取方式 | **纯规则**（连接词 + 句子切分） | 不调用模型：这是「把正文里已有的结构摆出来」，不是「判断它讲不讲得通」。后者是逻辑自检 |
| 逻辑链的呈现 | **段落序号 + 原句 + 连接词类型**，按原文顺序 | 作者要能一眼对回正文；排序变了就失去「链」的意义 |
| 逻辑链与问题清单的关系 | **并列两个面板** | 链是材料，问题是判断。混在一起会让作者以为「链里每一句都有问题」 |

## 3. 数据

**无新表、无迁移。**

- `foreshadow.status` 的取值由代码词表决定（`String(20)`），扩值不需要改表。
- 存量数据：`planned` / `confirmed` 两种。`confirmed` 是旧词表下「作者确认过的规划」，迁移到新词表时**不自动改**（改数据是危险动作）；序列化时把 `confirmed` 显示为「已确认（旧）」并提示作者可在账本里重设。

## 4. 服务设计

### 4.1 `foreshadow_types.py`

```
FORESHADOW_STATUSES = {planned: 规划中, planted: 已埋, paid: 已收, dropped: 已弃}
normalize_foreshadow_status(value, *, default="planned") -> str
```

### 4.2 派生与回收率（`foreshadow_service`）

```
effective_status(row) -> str          # 纯函数，见 §2 的派生规则
ledger_summary(session, project_id) -> dict
    {total, planned, planted, paid, dropped, rate}
```

`effective_status`：显式 `paid` / `dropped` 原样返回；显式 `planted` 但 `actual_pay_scene_id` 非空 → `paid`；`planned` 且 `actual_pay_scene_id` 非空 → `paid`；`planned` 且 `plant_scene_id` 非空 → `planted`。

### 4.3 逻辑链（`logic_chain.py`，纯函数）

```
extract_chain(text: str) -> list[dict]
    [{paragraph: int, sentence: str, kind: "cause"|"turn"|"reveal"}]
```

规则：

- 按空行切段、按句末标点切句。
- `cause`：含「因为 / 由于 / 所以 / 于是 / 因此 / 结果」。
- `turn`：含「但是 / 然而 / 可是 / 却 / 不料 / 谁知」。
- `reveal`：含「原来 / 才发现 / 竟是 / 终于明白」。
- 一句命中多个类型时取**第一个**命中的（按 cause → turn → reveal 的顺序），并记下命中的连接词。

**不做**：代词消解、跨段推理、是否成立的判断。

### 4.4 API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/projects/{id}/foreshadows/summary` | 四类计数与回收率 |
| GET | `/api/scenes/{id}/logic-chain` | 逻辑链（无正文时返回空列表与原因） |

`PATCH /api/foreshadows/{id}` 的 `status` 改用新词表。

## 5. 前端

- **伏笔账本**：顶部四个计数与回收率；筛选增加「已弃」；每一行显示有效状态（派生值），显式设置过时标出「已手设」。作者可改状态。
- **写作台**：右栏「逻辑链」面板（与逻辑自检问题清单并列），列出段落序号 / 类型 / 原句 / 连接词；空态说明「这一段没有明显的因果连接」。

## 6. 测试策略

| 层 | 内容 |
|---|---|
| 派生 | 六种组合（显式四态 × 位置字段有无）各一条 |
| 回收率 | `dropped` 不进分母；全空时为 0 不是 NaN |
| 词表 | `confirmed` 归一化、未知值报错 |
| 逻辑链 | 三类连接词各一条；一句多类型取第一个；无连接词不硬凑；空正文 |
| 接口 | 两条新路由的状态码与载荷；`PATCH` 用新词表 |
| 前端 | build + 走查 |

## 7. 风险

- **`confirmed` 存量**：不改数据，只显示为「已确认（旧）」并提示可重设 —— 静默改作者的数据比留一个略旧的标签糟。
- **逻辑链的误报**：「但是」在口语里常不构成真正的转折。文本视图是材料不是判断，误报的代价只是多一句；不因此收紧规则，但**不把它接入任何自动检查**。
