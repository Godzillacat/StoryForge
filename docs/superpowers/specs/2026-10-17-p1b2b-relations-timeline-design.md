## 1. 阶段定义

### 1.1 为什么这一段

P1b 只剩 **P1b-2b：关系网与时间线**。它们在 P1b 拆分为 2a / 2b 时就被划到这一段，理由不是体量，而是**依赖不依赖模型**：人物要扩世界观构建师的输出契约、必须尽早拿真实模型验证；关系网与时间线是作者手工维护的结构，不经过模型，拖后不卡验证。

这一段还要一并清掉三笔与「P1b 收尾」直接相关的欠账：

1. **`seed_agents` 预置更新到不了已有安装** —— P1b-2a 记为**交付阻塞**，要求「下一段之前处理」。根因是它按名字判「已存在就跳过」，代码里的新预置永远进不了旧库；P1b-2a 的人物契约是靠控制方手工用版本化接口装了一次才到达作者的库。
2. **P1b-2a 验收第 5 条只验了候选侧** —— 真实模型候选上的「采纳 → 落库 → 编辑器回显」没走过。
3. **保存非人物条目会把人物八项写成空串** —— 前端无条件提交八项，直接违反 P1b-2a「改类型保留八项」的裁定。

FTS5 不在本段。它服务正文检索，第一次真正需要是 P2 的上下文组装；P1c 是卷 / 章 / 场景卡设计，不依赖全文检索。**留到 P2 之前单独做。**

### 1.2 验收标准

1. **存量库启动**：迁移 v2 / v3 各执行一次；`entry_relation` 多出 `strength`，`agent` 多出 `preset_key`，`agent_version` 多出 `preset_fingerprint`；**原有数据一条不少、已有字段值不变**；再启动一次**不重复执行**。
2. **关系网**：在两条人物条目间建立 A→B（类型、强度 4）与 B→A（类型、强度 2），落库读回一致；关系可编辑、可删除；强度留空表示「未评」；强度 0 或 6 被拒。
3. **同时建立反向**：一次操作建立两条方向相反的关系；之后两条可各自独立改类型与强度。
4. **时间线**：新建三条事件，顺序可上移 / 下移；参与者与地点落库读回一致；删除一条人物条目后，事件里不再含该 ID；删除地点条目后，事件的 `location_id` 自动置空；跨项目条目、非人物参与者被拒。
5. **预置更新**：旧库启动后内置角色卡被认领并补写 `preset_key`，**不产生重复角色卡**；当前版本内容与当前预置一致时回填指纹，**不新建、不切换版本**；作者改过的版本不回填指纹、不提示更新，但提供「恢复预置」；应用预置会新建一版、保留作者的模型绑定、旧版本全部可回退；二次启动幂等。
6. **前端**：关系网页与时间线页可用；工作室对内置角色卡显示「预置有更新 / 恢复预置」；世界观编辑器保存非人物条目时不再提交人物八项。
7. **采纳路径验证**：在作者真实库的**副本**上，用上一轮真实模型产出的人物候选走通「采纳 → 落库 → 编辑器回显」。
8. **既有 243 条测试全绿**，并补齐本段新增测试。

### 1.3 明确不做

- **FTS5 全文检索** —— 留到 P2 之前。
- **逐章状态推进**（人物生死 / 身份 / 能力 / 所在地按章节记录）—— P1c 才有章节可挂。
- **关系图可视化** —— D-19 明确一期用表格、关系图二期。
- **AI 生成关系与时间线** —— §5.2 的设定师职责只有人物、势力、规则、术语；P1b-2a 已定「AI 不出关系候选」，时间线同理。两者纯手工维护，因此本段**不需要真实模型调用**（验收第 7 条用已有运行记录）。
- **关系的历史版本 / 审计** —— 属 P4 控制力深化。
- **跨项目关系与时间线** —— 一个项目内自洽即可。

## 2. 数据模型

### 2.1 关系网复用 `entry_relation`

不新建表。P1b-1 建它时就按两层的形状设计：有向边、`kind` 自由文本、项目内自洽；并明确写了「关系网额外需要强度，P1b-2 加上去时已有行不受影响」。

| 列 | 变化 | 说明 |
|---|---|---|
| `strength` | **新增**，`INTEGER NULL` | 1–5；`NULL` = 未评。旧关系一律为未评 |

- **有向**：A→B 与 B→A 是两条边，各自有类型、强度、备注。双向关系由两条边表达，**允许不对称** —— 「A 视 B 为恩人，B 未必视 A 为朋友」正是创作工具库模板要求记录的情形。
- **可编辑**：补 `PATCH`，改类型 / 强度 / 备注。起点与终点不可改（要换端点就删了重建），避免一条关系在编辑中悄悄变成另一对。
- **强度对所有关系类型可用**，不只人物之间。通用关联（「位于」「下属」）用不上就留空。
- **拒绝自环**：起点与终点相同的关系没有意义，创建时直接拒绝。这是对既有行为的收窄，记入变更记录。
- 不加强制唯一约束：同一对条目之间可以有多条不同类型的关系（「师父」与「恩人」可以并存）。

### 2.2 时间线新建 `timeline_event`

**不塞进 `setting_entry`。** 它是有序事件，不是条目：没有别名、标签、候选、类型归一化这些条目机制；而 `setting_entry` 已经有九个只对某一类条目有值的列，再往里加会继续把它变成几种实体的并集。

| 列 | 类型 | 说明 |
|---|---|---|
| `project_id` | FK → `project`，CASCADE，索引 | |
| `title` | String(200) | 必填 |
| `story_time` | String(200) | 自由文本的「故事内时间」，如「第三年·春」「十日后」 |
| `description` | Text，默认空串 | |
| `order_index` | Integer，索引 | 显式排序位 |
| `participants_json` | JSON，默认 `[]` | 人物条目 ID 列表；API 字段名叫 `participants` |
| `location_id` | FK → `setting_entry`，可空，`ON DELETE SET NULL` | 地点 |
| 时间戳 | 沿用 `IdMixin` / `TimestampMixin` | |

**为什么是「手排顺序 + 自由文本时间」**：故事可能用虚构历法、多历法或相对时间。把 `story_time` 当排序依据会让「第三年」与「十年后」按字典序排错；把它拆成结构化年月日又会卡死奇幻设定。显式 `order_index` 保证顺序永远可靠，`story_time` 只负责给人看。

- 新建事件追加到末尾（`max(order_index) + 1`，空为 0）；上移 / 下移与相邻事件**交换 `order_index`**。
- 删除后留下空档是允许的，不影响排序。
- 排序读回一律 `ORDER BY order_index, created_at`，即使历史数据出现同序也稳定。
- **参与者只收人物**（`type == "character"`），同一项目内，重复 ID 去重；地点收本项目任意条目 —— 地点可能被作者建成「势力」或「概念」，不硬性限制类型。
- 删除设定条目时：`participants_json` 里的该 ID 由服务层显式剔除（JSON 列不会被外键级联），地点由 FK 自动置空。
- 参与者条目**事后被改成非人物**时不回洗历史事件 —— 静默删掉作者填过的参与者比留着一条旧引用更糟；界面按当前名字显示，P2 做一致性检查时再处理这类引用。本条记入变更记录。

### 2.3 预置身份与指纹

预置更新需要两个新列，解决两个问题：

| 列 | 类型 | 解决什么 |
|---|---|---|
| `agent.preset_key` | String(60)，可空，**唯一索引** | 用代码里的稳定 key 认领内置角色卡。现在按**名字**判重：作者一改内置角色卡的名字，下次启动就会再建一个重复的。唯一索引允许多个 `NULL`，只约束真正的预置角色卡 |
| `agent_version.preset_fingerprint` | String(64)，可空 | 标记「这个版本来自哪一份预置内容」。没有它就无法区分「作者没改过的旧预置」与「作者改过的版本」 |

**指纹的计算范围**（规范化 JSON 的 SHA-256）：

- 计入：`system_prompt`、`context_slots_json`、`output_schema_json`、`param_profile`、`trigger_mode`。
- **不计入**：`model_binding_json`（作者的模型配置）、`skills_json`（当前预置不定义，保留作者勾选）、`note`（描述性文字，改了不该提示「预置有更新」）。
- 规范化：`json.dumps(..., sort_keys=True, ensure_ascii=False, separators=(",", ":"))`，保证同一内容在任何机器上同指纹。

指纹只存在版本上，不复制预置正文 —— 正文已经在版本里。

## 3. 迁移

两条新迁移，迁移语句**冻结成字面量**（历史记录，不跟可变常量走）：

| 版本 | 内容 |
|---|---|
| v2 | `ALTER TABLE entry_relation ADD COLUMN strength INTEGER` |
| v3 | `ALTER TABLE agent ADD COLUMN preset_key VARCHAR(60)`；`ALTER TABLE agent_version ADD COLUMN preset_fingerprint VARCHAR(64)`；`CREATE UNIQUE INDEX uq_agent_preset_key ON agent(preset_key)` |

- 只加可空列，不重建表，不触碰已有行。
- `timeline_event` 是**新表**，归 `create_all` —— 沿用「迁移永不建表」。
- 存量库：执行前自动备份（框架既有行为），每步一个事务，失败拒绝启动。
- 全新库：由当前模型直接建出，盖章为最新版本，不跑历史迁移。
- 迁移**不做数据回填**：`preset_key` 的认领依赖代码里的预置清单，放在 `seed_agents`（见 §6）；时间线没有历史数据要搬。

## 4. 关系网

### 4.1 服务层

- `create_relation(session, project_id, create_reverse=False, **fields)`：
  - 校验起点与终点存在、同项目、**不同**；
  - 校验 `kind` 非空、`strength` 为 1–5 或空；
  - `create_reverse=True` 时在同一事务里再建一条 `from`/`to` 互换的关系，初始类型 / 强度 / 备注相同，之后可独立编辑。
- `update_relation(session, relation_id, **fields)`：只接受 `kind` / `strength` / `note`；`kind` 给了就必须非空；`strength` 显式 `None` 表示清空为未评。
- 校验放在服务层（纯逻辑、可 pytest），Pydantic 只做类型与范围的第一道门。

### 4.2 API

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/projects/{id}/relations` | 既有，返回强度 |
| `POST` | `/api/projects/{id}/relations` | 增加 `strength`、`create_reverse`（不落库，只影响本次创建）；响应仍返回正向那条，反向那条由列表刷新看到 |
| `PATCH` | `/api/relations/{id}` | **新增**：改类型 / 强度 / 备注 |
| `DELETE` | `/api/relations/{id}` | 既有 |

`RelationCreate.strength: int | None = Field(default=None, ge=1, le=5)`；`RelationUpdate` 三个字段全部可选，路由用 `model_dump(exclude_unset=True)` 区分「没给」与「显式清空」。

### 4.3 前端

新增导航页「关系网」（`/relations`），与世界观、术语表平级。

- 默认只显示**人物↔人物**；可切「全部条目关联」；可按关系类型筛选。
- **按无序关系对聚合**：每对（甲、乙）一个卡片，分别列出甲→乙与乙→甲的每一条关系（类型 / 强度 / 备注）。某个方向没有记录时显示「未记录」并提供就地补录 —— 这直接对应创作工具库模板的检查问题「每条关系是否双向都记录，且允许两个方向的强弱不对称」。
- 新建表单：起点、终点、类型、强度、备注、「同时建立反向关系」（默认勾选）。反向那条初始与正向相同，界面提示作者按语义改成反向称谓（如「师父」的反向可能是「徒弟」）。
- 编辑与删除逐条进行；删除一个方向不影响另一个方向。
- 世界观页的条目编辑器保留关联区，补上**强度显示与选择**；完整的表格编辑在关系网页，避免两套编辑逻辑各自演化。

### 4.4 测试

- 创建带强度、强度越界、强度为空；自环被拒；跨项目端点被拒。
- `create_reverse` 生成两条，且可独立改；删一条另一条还在。
- `PATCH` 改类型 / 强度 / 备注；显式清空强度；空类型被拒。
- 服务层与 API 各覆盖一次（纯逻辑在服务层，边界在 API）。

## 5. 时间线

### 5.1 服务层

| 函数 | 行为 |
|---|---|
| `list_timeline(session, project_id)` | 按 `(order_index, created_at)` 排序 |
| `create_event(session, project_id, **fields)` | 校验标题、参与者、地点；追加到末尾 |
| `update_event(session, event_id, **fields)` | 改标题 / 时间标注 / 描述 / 参与者 / 地点；**不改顺序** |
| `move_event(session, event_id, direction)` | 与相邻事件交换 `order_index`；已在首 / 尾则原样返回（前端按钮禁用） |
| `delete_event(session, event_id)` | 删除 |

校验规则：

- 标题去空白后非空。
- `participants`：每个 ID 都必须存在、属于同一项目、类型为人物；重复 ID 去重并保持输入顺序。
- `location_id`：为空可接受；非空时必须存在且同项目，类型不限。
- 所有错误给中文可读原因，不抛 500。

`world_service.delete_entry` 增加一步：删除条目前，把所有事件 `participants_json` 中的该 ID 剔除。JSON 列必须**赋新列表**再提交（原地 mutate 不被 SQLAlchemy 跟踪）。地点由 FK 的 `ON DELETE SET NULL` 处理，需有测试证明 SQLite 外键真的生效。

### 5.2 API

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/projects/{id}/timeline` | 有序列表 |
| `POST` | `/api/projects/{id}/timeline` | 新建 |
| `PATCH` | `/api/timeline/{id}` | 编辑（不含顺序） |
| `POST` | `/api/timeline/{id}/move` | body：`{"direction": "up" \| "down"}` |
| `DELETE` | `/api/timeline/{id}` | 删除 |

响应返回原始 ID（`participants`、`location_id`）；前端已加载条目清单，自己映射名字，避免后端重复下发名称。

### 5.3 前端

新增导航页「时间线」（`/timeline`）：

- 竖向有序列表；每条显示时间标注、标题、参与者、地点、描述。
- 上移 / 下移按钮（首尾禁用）；编辑 / 删除。
- 新建与编辑表单：标题、故事内时间、描述、参与者多选（只列人物）、地点选择（列全部条目）。
- 空态说明：「时间线是故事内时序，不是写作顺序；顺序由这里的上下移动决定。」
- 页面按项目切换；请求失败要有可见提示（沿用世界观页的 notice 机制，但不重复它的已知 Minor）。

### 5.4 测试

- CRUD 往返；顺序追加；上移 / 下移；首尾移动不越界。
- 人物参与者校验（非人物、跨项目、不存在）；地点校验；重复参与者去重。
- 删除人物条目后事件参与者被清理；删除地点后 `location_id` 为 `None`。
- 两个项目的事件互不可见。

## 6. 预置更新（显式）

### 6.1 认领内置角色卡

`seed_agents` 不再按名字判重。每个预置条目按以下顺序认领已有角色卡：

1. `Agent.preset_key == 预置 key` → 认到。
2. 否则，`builtin=True` 且 `preset_key IS NULL` 且名字相同 → 认领，补写 `preset_key`。
3. 否则，`builtin=True` 且 `preset_key IS NULL` 且 `task_type` 相同且**只有一个**候选 → 认领，补写 `preset_key`（应对作者改过名字的情况）。
4. 都找不到 → 新建角色卡与 v1，写入 `preset_key` 与指纹。

- 只认领 `builtin=True` 的角色卡；作者自建的同名角色卡不冒充预置。
- 认领到之后**只回填指纹，不新建、不切换版本**。
- 二次启动幂等。
- 如果某一步出现多个候选（理论上不该发生），不认领、也不新建，避免制造重复；下一次启动仍会尝试。

### 6.2 回填指纹

对认领到的角色卡，看当前版本：

- 没有指纹，且其内容投影（§2.3 的五个字段）与代码里的当前预置**逐字段一致** → 回填指纹。P1b-2a 控制方手工装成 v3 的世界观构建师正好走这条，回填后就能识别后续更新。
- 没有指纹，内容不一致 → 视为作者已改过，**不回填**。
- 已有指纹 → 不动。

### 6.3 应用预置

`POST /api/agents/{agent_id}/apply-preset`：

- 角色卡必须有可解析的 `preset_key`，否则 400。
- 当前版本已是最新预置（指纹相同）→ 400「预置已是最新」。
- 否则用当前代码里的预置创建一个新版本：
  - 内容取预置的五个指纹字段 + `note`；
  - **`model_binding_json` 与 `skills_json` 不取预置，继承当前版本** —— 那是作者的配置；
  - `version_no = max + 1`，写入指纹，设为当前版本；
  - 旧版本全部保留，可回退。
- 返回值带新的预置状态。

**版本编辑绝不继承指纹**：`create_version` 新建作者版本时必须把 `preset_fingerprint` 留空。否则作者改一版，系统会误以为它仍是未改动的预置，下一次更新就会覆盖掉作者的修改。这条有专门测试。

### 6.4 状态与界面

`_agent_out` 增加 `preset` 段（由服务层算，路由只投影）：

| 字段 | 含义 |
|---|---|
| `key` | `preset_key`，无预置为 `null` |
| `update_available` | 当前版本有指纹，且不等于当前预置指纹 |
| `can_restore` | 有预置，且当前版本无指纹或与预置不同（可恢复/应用） |
| `up_to_date` | 当前版本指纹等于当前预置指纹 |

工作室对每个内置角色卡显示：

- `update_available` → 「预置有更新」＋按钮「应用预置更新」。
- `can_restore` 且非 `update_available` → 「恢复预置」按钮。
- 两者都需确认弹窗，写明「会新建一版并设为当前；旧版本保留，可回退」。

启动时**不做任何自动切换**。这正是「作者握着方向盘」在预置更新上的落法。

### 6.5 测试

- 全新库：预置角色卡带 `preset_key` 与指纹。
- 旧库模拟（无 `preset_key` / 指纹、内容与当前预置一致）：启动后认领 + 回填，不新增版本。
- 内容不一致：不回填；状态 `can_restore`，不是 `update_available`。
- monkeypatch 预置内容后：`update_available`；应用预置新建一版、设为当前、保留模型绑定、旧版本还在；再次应用 → 400。
- `create_version` 不继承指纹。
- 改名后启动不产生重复角色卡（按 `task_type` 认领）。
- 二次启动幂等。

## 7. 收尾项

### 7.1 世界观编辑器的人物字段守卫

现状：前端保存条目时无条件把八个字段一起提交。对非人物条目，编辑器不渲染这些字段、草稿初始化成空串，于是「把人物改成势力再保存」会把八项**清空** —— 直接违反 P1b-2a「改类型时八项保留」的裁定。

修法：只有当前类型为人物时才提交八个字段。要改三处：

- `World.tsx` 的手工保存；
- `World.tsx` 的候选采纳（同一份 `...next.fields` 展开）；
- `EntryEditor.tsx` 的 `characterFieldsOf`：源条目不是人物时返回空对象，避免给非人物草稿预置八个空串。

后端的 `_entry_fields` 已经是 `model_dump(exclude_unset=True)`，省略即不改；因此不需要动服务层。加一条后端测试钉住「更新时不带这些键，不会清空已有值」，前端行为归入手工走查。

### 7.2 采纳路径验证

P1b-2a 验收第 5 条只验了候选侧。补验方法不消耗新额度：

1. 用 SQLite 的备份 API 把作者真实库复制到临时数据目录（连同 WAL 一起做一致性快照；**不动原库**）。
2. 用 `STORYFORGE_DATA_DIR` 指向副本启动应用。
3. 找到上一轮真实模型运行产生的人物候选，走「采纳 → 落库 → 世界观编辑器回显」。
4. 核对：`setting_entry` 的八个字段与候选一致、`source_run_id` 指向那次运行、术语投影里出现姓名与称呼。

若副本里没有可用的人物候选，再在确认阿里云百炼额度后做一次真实调用。

### 7.3 P1c 的准备

本段不写 P1c 设计。收口后，P1c 需要的是**卷 / 章 / 场景卡**三张新表与章节树界面，与关系网、时间线没有数据依赖；时间线可以在 P1c 的场景卡里被引用，但不是前置条件。P1c 设计另起一轮，按同样的「设计 → spec → 计划 → 实施」流程走。
