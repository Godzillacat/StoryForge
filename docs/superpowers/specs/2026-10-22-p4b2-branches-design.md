# StoryForge P4b-2 设计：场景正文分支

> 2026-10-22。P4b 的后半段（P4b-1 已交付快照与改动历史）。产品 §3.4 / §4.11 要求「一个场景可以开多个分支并行推进，对比后再合并或丢弃；分支树能看清一部作品走过哪些岔路」。

## 1. 阶段定义

### 1.1 这一段要解决什么

作者写到一个转折点时常常不确定往哪走。今天他能做的只有：写一版 → 保存 → 再写一版覆盖掉 → 靠 `scene_revision` 翻回去。**修订历史是线性的**：它记的是「这个场景曾经是什么」，不是「另外两种写法各自长成什么样」。想同时推进 A、B 两案，只能靠复制到别处手管，而那会立刻脱离开采纳 / 审校 / 回写 / 检索这一整套。

P4b-2 交付：**同一个场景下可以并存多条正文分支**，每条都能独立生成、编辑、审校，最后**选一条合并为主版**（其余保留为分支，可继续留着或丢弃）。

### 1.2 验收标准

1. **开分支**
   - 可从一个场景开新分支，命名；新分支以**当前已采纳正文**为起点（没有正文则从空开始）。
   - 分支名在同一场景内唯一；主版本身不是分支。
2. **分支里能干活**
   - 分支有自己的正文；可手工保存、可生成（流式）、可采纳草稿、可看修订历史。
   - **生成与采纳走与主版完全相同的链路**（锁定、段落锁、改动历史、检索都生效），只是写进的是分支而不是主版。
3. **对比**
   - 可把任意两条正文并排对比（直接复用现有的 `DiffPanel` 的行级 diff）。
4. **合并 / 丢弃**
   - **合并** = 把某条分支的正文采纳为主场景正文：主版旧正文进 `scene_revision`（来源 `branch`），分支本身**保留**（合并不等于删除，作者可能还要回去）。合并受锁定与段落锁约束。
   - **丢弃** = 删除分支及其正文；主版不受影响。
5. **可追溯**
   - 每次开分支 / 合并 / 丢弃都进改动历史。
6. **基线**：后端既有 851 条全绿；前端 30 条全绿、`pnpm build` 干净。
7. **本段不调用模型**：行为是确定性的，用临时数据目录与浏览器走查。

### 1.3 明确不做

- **分支整张场景卡** —— 已定：分支只是正文的并行实验。场景卡（目标 / 冲突 / 转折 / 人物 / 地点）是**共享**的：A、B 两案写的是同一场戏的不同写法，不是两场不同的戏。分支整张卡会立刻带来「伏笔链接冲突」「哪张卡的锁定算数」这类没有好答案的问题。
- **分支树 / 图形化** —— 每个场景的分支是**一层**（分支不能再分支）。产品说的「分支树」在一层就够表达「这部作品走过哪些岔路」；多层会需要合并语义与冲突解决。
- **多条分支自动合并** —— 合并是「整份替换成某一条」，不做三方合并。
- **分支跨场景** —— 分支属于单个场景。
- **快照包含分支** —— 快照是「作品结构 + 主版正文」；分支是实验材料，不进快照（进了会让回滚把实验也回滚掉，而作者回滚的往往是主版结构）。

## 2. 已定决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 分支范围 | **只分支正文** | 场景卡是共享的戏；分支是同一场戏的不同写法。见 §1.3 |
| 新分支的起点 | 复制**当前主版正文** | 作者的典型路径是「主版写得差不多了，想试另一版」。从空开始会让他重打一遍已经满意的部分 |
| 分支名唯一性 | 同一场景内唯一 | 作者要能说「合 A 案」 |
| 分支存储 | 新表 `scene_branch`，一行一条分支，正文存在该行 | 与 `scene_draft` 分开：草稿是「一次生成的待审材料」，分支是「一条持续的写法」。混在一起会让「采纳」与「合并」两个动作打架 |
| 锁定的作用 | 与主版**相同**：场景有效锁定 → 分支里不能生成 / 采纳 / 合并 | 锁定是「AI 不许碰这里」，分支里的 AI 也是 AI。作者手工作业不受限 |
| 段落锁的作用 | 分支**采纳草稿**时同样强制；**合并**时同样强制 | 段落锁保护的是「这几句话必须一字不改地留在这一场里」，与写在哪条分支无关 |
| 合并的去向 | 分支正文 → `scene.body`；旧主版进 `scene_revision`（新来源 `branch`） | 复用现有修订机制，合并后可「恢复修订」退回；不必另造一套历史 |
| 合并后分支是否删除 | **保留** | 合并是「我选这条作主版」，不是「其余作废」。作者可能还要回去继续改 |
| 生成写到哪里 | 分支有自己的草稿（`scene_branch` 上一条 `draft_json` 不够用 → 见 §3） | 复用 `scene_draft` 会与主版草稿冲突（每场景至多一条） |
| 检索 | 分支正文**不进 FTS** | 索引服务的是「写这一场时该看到哪些设定」，分支是未定稿的旁路；进索引会让主版的检索命中被实验稿污染 |
| 快照 | **不含分支** | 见 §1.3 |

## 3. 数据

### 3.1 `scene_branch`（新表，`create_all`，**无迁移**）

| 列 | 类型 | 说明 |
|---|---|---|
| id | str(36) | |
| scene_id | FK scene CASCADE，索引 | |
| name | str(120) | 场景内唯一（`uq_branch_scene_name`） |
| content | text | 该分支的正文 |
| draft_content | text | 该分支的 AI 草稿（可空串） |
| draft_run_id | str(36) NULL | 生成该草稿的运行记录 |
| note | text | 作者备注 |
| created_at / updated_at | | |

**草稿直接挂在分支行上**，不建第三张表：每个分支至多一条草稿，与 `scene_draft` 的约束同形，但生命周期完全跟着分支走 —— 丢弃分支时草稿自然消失。

### 3.2 `scene_revision.source` 新增取值 `branch`

不新增列；`source` 本来就是自由字符串（`ai` / `author` / `restore`）。加一个 `branch` 让作者在修订历史里看得出「这一版是从分支合进来的」。

## 4. 服务设计

### 4.1 `branch_service.py`

```
create_branch(session, scene_id, name, note) -> SceneBranch   # 从主版正文起步
list_branches(session, scene_id) -> list[dict]
get_branch(session, branch_id) -> dict
rename_branch(session, branch_id, name, note)
save_branch_body(session, branch_id, content) -> dict          # 手工作业，不受锁限制
save_branch_draft(session, branch_id, content) -> dict
adopt_branch_draft(session, branch_id) -> dict                 # 受锁定 + 段落锁约束
merge_branch(session, branch_id) -> dict                       # 合入主版，受锁定 + 段落锁约束
discard_branch(session, branch_id) -> None
```

**合并的步骤**（一个事务）：

1. 查场景的有效锁定 —— 锁定则拒绝（与「采纳草稿」同一条路）。
2. 查段落锁 —— 分支正文若缺已锁段落则拒绝并列出。
3. 旧主版正文若非空 → 写一条 `scene_revision(source="branch", note="合并分支「X」前的主版")`。
4. `scene.body = branch.content`。
5. 写改动历史（`target_type=scene`、`action=adopt`、`source=author`、摘要说明来自哪条分支）。
6. 主版旧问题标 `superseded`（复用 `text_service._supersede_audit`）。
7. 主版进 FTS 脏标记。

**分支里的生成**：`POST /api/branches/{id}/generate` 走与主版相同的准备链路（`prepare_generation` 的锁定/上下文部分），把结果写进 `branch.draft_content`。**不复用** `text_service.create_run` 的草稿落点（那会写主版草稿）。

### 4.2 改动历史接入

| 位置 | action | summary |
|---|---|---|
| create_branch | create | 「从主版开分支」 |
| merge_branch | adopt | 「合并分支『X』（N 字）」 |
| discard_branch | delete | 「丢弃分支『X』」 |

### 4.3 对比

纯前端：拉主版正文 + 分支正文，复用 `DiffPanel`。不新增后端接口。

## 5. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/scenes/{id}/branches` | 分支列表（不含正文，只有字数与时间） |
| POST | `/api/scenes/{id}/branches` | `{name, note}`，从主版正文起步 |
| GET | `/api/branches/{id}` | 详情含正文与草稿 |
| PATCH | `/api/branches/{id}` | 改名 / 备注 |
| PUT | `/api/branches/{id}/body` | 手工保存 |
| PUT | `/api/branches/{id}/draft` | 保存草稿 |
| POST | `/api/branches/{id}/adopt` | 采纳该分支的草稿 |
| POST | `/api/branches/{id}/merge` | 合入主版 |
| POST | `/api/branches/{id}/generate` | 流式生成到该分支的草稿（SSE） |
| DELETE | `/api/branches/{id}` | 丢弃 |

错误码：场景 / 分支不存在 404；重名 400；锁定或段落锁 409（与主版一致）。

## 6. 前端

- **写作台**：右栏新增「分支」面板 —— 列表（名称 / 字数 / 草稿标记）、新建、改名、丢弃；选中分支后正文区在「主版 / 该分支」之间切换；「与主版对比」按钮展开 diff；「合入主版」二次确认（明示会替换主版正文、旧版进修订历史）。
- 分支里生成 / 采纳 / 保存都复用现有按钮，只是目标不同。

## 7. 测试策略

| 层 | 内容 |
|---|---|
| 服务 | 新建从主版起步、重名、改名、保存、采纳草稿、合并（含修订来源 `branch`）、丢弃 |
| 锁定 | 场景锁定时分支内生成 / 采纳 / 合并被拒；作者手工保存不受限 |
| 段落锁 | 分支采纳与合并都强制；缺段落时列出 |
| 隔离 | 分支正文不进 FTS、不进快照、不影响主版草稿 |
| 历史 | 开 / 合 / 丢三条记录 |
| 接口 | 十条路由的状态码与载荷 |
| 前端 | build + 浏览器走查 |

## 8. 风险

- **分支与主版草稿同名冲突**：一个场景同时有主版草稿与分支草稿时，界面上必须始终标清楚「你正在看哪一条」。正文区顶部固定显示当前目标。
- **合并后误以为分支已删**：合并后分支保留，界面要明示「分支仍在」。
- **忘了几条分支在跑**：写作台的章节树在场景上标一个小角标显示分支数。
