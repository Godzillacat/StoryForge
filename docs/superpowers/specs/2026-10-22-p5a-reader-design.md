# StoryForge P5a 设计：阅读器与朗读

> 2026-10-22。P5 的第一段（P5b EPUB 精修、P5c pywebview 外壳与打包随后）。
> 产品 §4.8 要求：阅读器（章节树、分页与滚动、仿纸张与夜间主题、字号行距、进度、全文检索）、朗读（系统 TTS）。

## 1. 阶段定义

### 1.1 这一段要解决什么

到今天为止，StoryForge 能策划、能写、能审，但**作者没有一处可以「像读者那样读一遍」**。
写作台是按场景的工作界面：左边结构树、右边审校面板，中间一个 Markdown 源码框。
想通读成品只有导出文件再拿别的软件打开 —— 而导出是外部动作，读完想回头改一处
还得切回来找场景。

朗读同理：产品 D-17 定的是系统 TTS、零成本、离线可用，一文未写。

**这一段不产生任何新的写作能力，只把已写的正文变成「可以读的成品」。**

### 1.2 验收标准

1. **整本阅读**
   - `/read` 页：左侧章节树（卷 → 章，只列有正文的章），右侧正文，可滚动连续阅读。
   - **一次请求取回整本正文**（`GET /api/projects/{id}/book`），不按场景逐个拉 ——
     一本三十章的书写台要发三十次请求，阅读器不该重复这个错误。
   - 正文按 **Markdown 渲染**（标题、段落、引用、强调、分隔线），不是直接把源码倒给作者看。
   - 空章（没有已采纳正文）在树里标出、不可点；整本无正文时给出明确空态。

2. **阅读体验**
   - **仿纸张 / 夜间 / 护眼**三套主题，互相独立于应用外壳的配色。
   - **字号**（4 档）与**行距**（3 档）可调，**跨会话记住**。
   - **阅读进度**：记住每本书读到哪一章、滚到哪个位置；重新打开时回到那里，并给出「继续阅读」提示。
   - **全文检索**：在阅读器内检索，点结果跳到那一章并**高亮命中处**。

3. **朗读**
   - 用浏览器 `speechSynthesis`（系统 TTS），**不引入任何依赖、不联网、零成本**。
   - 可读**当前章**（从当前滚动位置起读）或**暂停 / 继续 / 停止**。
   - 朗读时当前句（或当前段）高亮跟随，作者看得出读到哪里。
   - **系统没有可用语音时明确说明**，不假装在读。

4. **基线**：后端既有 922 条全绿；前端 33 条全绿、`pnpm build` 干净。
5. **本段不调用模型**。

### 1.3 明确不做

- **分页翻页模式**（原文写「分页与滚动」）—— 只做**滚动**。理由：屏幕尺寸与字号随时变，
  分页要重新计算页边界，而滚动在长篇里本来就是更常见的读法；分页留到真的有人要。
- **云 TTS** —— D-17 明确先用系统 TTS；云 TTS 是可选后置项。
- **朗读全文**（跨章自动续读）—— 先把「读这一章」做对。跨章续读牵涉章节切换与进度一致，
  是另一个决定。
- **阅读器内编辑** —— 阅读就是阅读。要改去写作台。
- **EPUB 精修** —— P5b。

## 2. 已定决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 取正文的方式 | **新增 `GET /api/projects/{id}/book`，一次返回整本** | 书是整体；按场景逐个拉会让三十章的书发三十次请求，还要在前端拼顺序。导出服务已经在做同一件事（`_book_chapters`），两者口径必须一致 |
| 正文渲染 | **前端渲染 Markdown**，不引入重型依赖 | 项目已有「不用重型依赖解决可手写的小问题」的先例（JSON Schema 子集校验）。阅读需要的是标题 / 段落 / 引用 / 强调 / 分隔线这一个子集，一个百行渲染器够用，且**纯函数可测** |
| 渲染在哪一层 | **`lib/markdown.ts` 纯函数 → 结构化节点**，组件只负责画 | 渲染逻辑落在 `lib/` 才能被 vitest 覆盖；写成 JSX 就落进「UI 不写自动化测试」的盲区 |
| XSS | **不用 `dangerouslySetInnerHTML`**，用节点树渲染成 React 元素 | 正文里出现 `<script>` 不该被执行。节点树天然安全，也省掉一遍转义 |
| 主题 | 阅读器自己的三套主题，不跟应用外壳走 | 夜间写作台的深蓝与夜间阅读的暖黑不是一回事；作者读稿和写稿是两种状态 |
| 偏好存储 | **`localStorage`**，键按项目区分进度、按全局存主题与字号 | 这是本机偏好不是作品数据，进数据库要迁移、要快照、要同步，都是不值得的复杂度 |
| 朗读实现 | **浏览器 `speechSynthesis`** | D-17；零依赖、离线、零成本。代价是音色由系统决定，且各浏览器行为有差异 —— 如实记在遗留里 |
| 朗读单位 | **按段落**排队，一段一个 `SpeechSynthesisUtterance` | 单条长 utterance 在很多系统上会在中途断掉，且无法可靠暂停；分段排队才能做「暂停 / 继续 / 跳到下一段」与高亮跟随 |
| 检索跳转 | **复用现有 `/search` 接口**，阅读器自己过滤成「章」级结果 | 检索索引已经覆盖正文（P2a 起）；阅读器不需要第二套检索 |

## 3. 数据

**无新表、无迁移。**

- 整本正文由现有 `volume` / `chapter` / `scene.body` 组装，不落任何派生表。
- 阅读偏好全部在 `localStorage`。

## 4. 服务设计

### 4.1 整本正文（`export_service` 已有 `_book_chapters`，复用）

新增 `build_book(session, project_id) -> dict`：

```
{
  "project_id", "project_name", "total_words",
  "volumes": [
    {"id", "seq", "name",
     "chapters": [
       {"id", "seq", "title", "word_count",
        "paragraphs": [...]       # 已拼好的正文段，Markdown 原文
       }
     ]}
  ]
}
```

- **只收有正文的章**（与 `build_markdown` / `build_epub` 同一口径，`_book_chapters` 已如此）。
- 章内正文按场景顺序用空行拼起来，与导出**逐字一致** —— 读到的就是导出的。

### 4.2 API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/projects/{id}/book` | 整本正文（只含有正文的章）；项目不存在 404 |

### 4.3 前端纯函数（`lib/`）

- `parseMarkdown(text) -> MdBlock[]`：段落 / 标题 / 引用 / 分隔线 / 无序号列表；行内强调与代码。
- `readingProgressOf(book)`、`findMatches(text, query)`：检索命中的定位（块序号 + 偏移）。
- `speechChunksOf(blocks)`：把渲染后的块拍平成可朗读的纯文本段（去 Markdown 标记）。

全部纯函数，vitest 覆盖。

## 5. 前端

`/read` 页，导航加「阅读器」。

- 左栏：卷 / 章树，只列有正文的章；当前章高亮；无正文的章灰显并标「未写」。
- 右栏：正文区（三套主题）、顶部工具条（主题 / 字号 / 行距 / 朗读 / 检索）。
- 朗读面板：读当前章、暂停 / 继续 / 停止、当前段高亮。
- 检索框：结果列表（章名 + 片段），点击跳到该章并高亮。

## 6. 测试策略

| 层 | 内容 |
|---|---|
| 整本正文 | 只含有正文的章；与 `build_markdown` 的内容一致；项目不存在 404；空项目 |
| Markdown | 段落 / 标题 / 引用 / 分隔线 / 列表 / 强调；**HTML 标签原样当文字，不解释** |
| 朗读分段 | 去标记、空段跳过、顺序不变 |
| 检索定位 | 命中偏移正确、跨块不串 |
| 前端 | build + 浏览器走查（含真实点击朗读按钮） |

## 7. 风险

- **`speechSynthesis` 在不同 WebView2 / Edge 版本上行为不一**（音色、可用语言、暂停语义）。
  实现必须**先探测可用语音再决定是否显示朗读按钮**，探测不到就说明原因。这是浏览器能力，
  不是产品缺陷 —— 记为遗留，不做兜底 TTS。
- **整本正文可能很大**（百万字约几 MB）。一次返回是可接受的：这是本机回环，不经过网络；
  真到瓶颈时再分卷，不预先优化。
- **高亮跟随朗读**依赖 `onboundary` 事件，不是所有系统都支持；不支持时退化为「按段高亮」。
