# 生成修订建议 · 逐条确认 · 设计

> 二期第二项，兑现产品设计文档 §3.3 的第二个选项：**「生成修订建议逐条确认」**。
> P4a 当时把它显示为不可用并注明「后续提供」，理由写在 CLAUDE.md 2026-10-22 变更记录里 ——
> 那是一条新的 AI 执行路径，需要自己的提示词、契约与真实模型验证。

## 1. 意图

影响面面板现在给两条路：**只改上层，下游标为待复核**，或者**取消**。第一条只把问题推给作者自己，
第二条什么也没做。缺的那条是：**AI 把下游要跟着改的地方写成具体建议，作者逐条点头**。

作者改的往往是一句话（「主角动机从为父报仇改成替妹妹赎罪」），但下游有十几处场景卡与章摘要
还写着旧动机。逐条手改要一下午；全标待复核只是把这份工作换个地方记着。修订建议把「改哪儿、
改成什么、为什么」摆出来，作者只做采纳/不采纳两个动作。

## 2. 目标 / 非目标

**目标**

1. 在影响面面板里，针对**当前目标**跑一次模型，产出 **1–12 条**结构化修订建议。
2. 每条建议带：对象（场景 / 章）、字段、现值、建议值、理由。作者**逐条勾选**后一次性应用。
3. 应用是**作者动作**：只有勾选的才写库，每写一条记一条改动历史；锁定的对象不生成、也不应用。
4. 应用前**复核现值**：生成后被改过的对象不再套用旧建议，逐条报「已变化，跳过」。

**非目标**

- **不改正文**。建议只落在结构化字段（场景卡的目标 / 冲突 / 转折、章的摘要）。正文改动要走
  「生成 → diff → 采纳」，那是 P2a 已有的路径，也有自己的锁定语义；把正文塞进这套逐条确认里，
  等于绕过 diff。
- 不做自动应用、不做流式、不做多方案对比（A/B 是第三项）。
- 不覆盖设定条目 / 伏笔 / 时间线；它们出现在影响面清单里，但这一版只提示「需要你自己看」。

**反目标**

- 不能把「没勾选」当成「标为待复核」—— 两者是不同动作，混在一起作者就分不清自己答应过什么。
- 不能因为模型返回的标签对不上就**猜**一个对象；对不上就丢弃并计数。

## 3. 方案

### 3.1 数据流

```
作者点「生成修订建议」
  → POST /api/projects/{id}/impact/revisions  {target_type, target_id}
     ├─ 复用 impact_service.analyze() 拿到受影响清单
     ├─ 只保留可建议的对象（scene / chapter）且**未锁定**
     ├─ 组装上下文：目标自身内容 + 故事圣经 + 这些对象的现值（截断到 12 条）
     ├─ 跑「修订建议师」（task_type = revision_suggest），一次非流式调用
     ├─ 契约校验 → 解析 target_label → 映射回 id（未知标签丢弃并计数）
     └─ 把建议**存在 generation_run 的结果里**（不建新表）
  → 面板逐条勾选
  → POST /api/projects/{id}/impact/revisions/apply  {run_id, accepted: [index...]}
     ├─ 从 run 里读回建议（不在请求里回传正文，避免前端篡改写入内容）
     ├─ 逐条：字段白名单 → 对象未锁 → 现值 == 生成时的 before
     ├─ 写字段 + change_service 记一条改动历史
     └─ 返回 applied / skipped（每条带原因）
```

**为什么把建议存在 `generation_run` 里**：与「世界观候选」「章纲候选」同一套先例 —— AI 产出先落
运行记录、作者采纳才进业务表（D-04）。不建 `revision_suggestion` 新表，因为建议的生命周期就是
「一次运行 → 一次确认」，没有跨运行的查询需求。

**为什么应用时只收下标**：请求里若回传 `after`，前端就成了写入内容的来源；服务端从自己存的
运行结果里取值，前端只能选「哪几条」。

### 3.2 建议的形状

```json
{
  "target_label": "第1卷 第3章 场景2",
  "field": "goal",
  "before": "把玉佩交给掌柜",
  "after": "把妹妹的赎金交给掌柜",
  "reason": "动机已改为替妹妹赎罪，这一场的目标仍写着「玉佩」，与新的动机没有关系"
}
```

- `field` 白名单：场景 `goal / conflict / turn`；章 `summary`。其它一律丢弃。
- `before` 由**服务端**在生成时填（不是模型给的），应用时用它做现值比对。
- 同一对象同一字段只保留第一条（模型偶尔重复）。

### 3.3 智能体

新增预置角色卡 **修订建议师**（`preset_key = "revision-advisor"`，`task_type = "revision_suggest"`）：

- 槽位：`story_bible`、`project_core`、新增 `impact_target`（本次改了什么）与 `impact_candidates`
  （受影响对象的现值清单）。两个新槽位只在这次运行里组装，不做通用投影。
- 输出契约：`{ suggestions: [{target_label, field, after, reason}] }`，字段说明由契约自动注入
  （沿用 P1a 收口时的机制），提示词里不手写英文键。
- 模型：走 P3 的任务分路（`revision_suggest`）；没配就用默认服务商 + 绑定模型，仍取不到则给
  可读中文错误，不静默回落到服务商显示名（P1a 的教训）。

### 3.4 界面

影响面面板里那个禁用的按钮变成可点，就地展开：

```
生成修订建议    [3 条建议 · 采纳选中 2 条]  [全部不要]
□ 第1卷 第3章 场景2 · 目标
  现在：把玉佩交给掌柜
  建议：把妹妹的赎金交给掌柜
  理由：动机已改为替妹妹赎罪，这一场还写着「玉佩」
□ 第2章 · 摘要 （锁定，不可选）
```

- 锁定对象：建议区显示但 checkbox 禁用、标「锁定」；服务端也不生成（双重）。
- 「已变化」的行：应用后返回里标出来，红色文案说明现值已变、未套用。
- 生成中按钮转「生成中…」；失败给中文原因，不展示半截 JSON。

## 4. 边界

| 情况 | 行为 |
|---|---|
| 影响面为空 | 按钮禁用，提示「没有可建议的下游对象」 |
| 受影响对象全是锁定 | 同上，并说明「都在锁定中」 |
| 模型返回 0 条 | 显示「这次没有需要改的地方」，不报错 |
| 模型返回未知标签 | 丢弃并计数，在响应里带 `dropped` |
| 模型返回 20 条 | 只取前 12 条（提示词也要求 ≤12），其余丢弃并计数 |
| 运行中途被取消 / 失败 | 不落建议；界面给原因，可重跑 |
| 应用时对象已锁 | 跳过，原因「已锁定」 |
| 应用时现值与 before 不同 | 跳过，原因「现值已变化」 |
| 同一批重复应用 | 第二次全部命中「现值已变化」或「已应用」，幂等 |

## 5. 测试

| 层 | 内容 |
|---|---|
| pytest | 影响面过滤（只留 scene/chapter 且未锁）；标签映射与丢弃计数；字段白名单；12 条上限；应用时的锁 / 现值 / 未知下标；改动历史确实记了一条；运行记录里存了建议 |
| vitest | 响应到视图的纯函数（分组、可选项、计数） |
| 真实模型 | 一次真实调用：改一条人物动机 → 场景/章建议能引用新动机、`after` 是具体改法；采纳一条后落库并出现在改动历史 |
| 走查 | 面板生成 / 勾选 / 应用 / 锁定禁用 / 重跑 |

## 6. 明确不做

- 正文修订与 diff（走 P2a 的生成 → 采纳）。
- 建议的版本对比、跨运行合并。
- 设定条目字段的建议（需要另一套「字段级 diff」的安全模型）。
