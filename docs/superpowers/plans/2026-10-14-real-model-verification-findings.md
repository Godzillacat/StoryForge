# P1a 真实模型验证 · 发现记录

> 2026-10-14 · 这是一次 spike（探测），产出是**答案**，不是要保留的代码。
>
> 目的：补上 P1a 验收记录里两项「未验证」——交互式浏览器走查、模型产出质量。
> 方法：真实 uvicorn + 真实 Vite + headed Edge 驱动走查；真实服务商（阿里云百炼）跑通灵感解析与架构推荐。

---

## 1. 结论

**模型产出质量完全可用，甚至相当好。挡住产品的是接线，不是模型。**

用真实输入跑出的三套架构方案，每一套都引用了灵感解析卡里的具体字段值、给出适配度／风险／篇幅分配／节奏形态／不适用情形／杂交层，并且**通过了应用自己的输出契约校验**（`apply_contract` → `valid: True`）。故事圣经 v0 的三幕比例合计 1.0，五个人物一律写作「（待命名）」而非编造姓名。

但这条链路**在应用里跑不通**，原因有三个阻断级缺陷，全部与模型能力无关。

## 2. 阻断级缺陷

### 2.1 提示词与输出契约的键名不一致（两个智能体都有）

| 智能体 | 契约要的键 | 提示词里说的 |
|---|---|---|
| 灵感解析师 | `genre` `premise` `protagonist_desire` `conflict_source` `open_questions` | 「题材、子类型、一句话前提、主角欲望、核心冲突源…」 |
| 架构师 | `options` `story_bible_v0`（含嵌套 `tool` `reason` `fit_score` `risks`…） | 一个英文键都没出现 |

提示词从未告诉模型 JSON 的键名必须用英文，模型忠实执行中文指令 → 返回中文键 → 契约校验必失败 → 降级为纯文本。

**后果**：上位文档 §5.5 把结构化输出定为「AI 产出即可编辑物件」成立的前提。真实条件下它**一次都没成立过**。前端永远只拿到「未结构化」纯文本块，解析卡字段逐项编辑（P1a 验收 §1.2 第 3 条）形同虚设。

**为什么 127 个 pytest + 19 项冒烟全过却没抓到**：全程没有真实模型。假传输层返回预先写好的、英文键的 JSON —— 测试把「提示词」与「契约」分开验，没有一条断言要求两者一致。**缺的是一条跨产物一致性测试。**

**已验证的修法**（走接口建新版本，未改代码）：提示词里补上键名映射后，解析卡立即渲染为可逐项编辑的结构化字段，架构推荐产出通过契约校验。

**已定修法**：提示词给键名映射 **+ 渲染层从 `output_schema` 自动生成键名说明并注入**。后者从机制上消灭这类不一致——作者改契约时提示词自动同步，不必人工维护。

### 2.2 120 秒硬超时 + 非流式调用，架构推荐必然失败

- `llm.py:88`：`HttpxChatClient(timeout: float = 120.0)`，写死；`DEFAULT_SETTINGS` 里没有超时字段，角色卡也没有。
- `execute.py:94`：运行时走 `client.complete()`（**非流式**）。`llm.py` 里的 `stream()` 存在但运行时从不调用。

实测（同一提示词、同一参数 `temperature 0.7 / max_tokens 4096`）：

| 模型 | 应用内结果 | 直连服务商结果 |
|---|---|---|
| `qwen3.8-max-0902` | 121.3s → `error` timeout，0 completion tokens | — |
| `qwen3.8-flash` | 121.4s → `error` timeout，0 completion tokens | **139.5s → 200 OK，完成** |

任务**能跑完，需要 139.5 秒**，只差约 20 秒。换成 flash 也一样超时——这不是模型强弱问题，是上限设低了，且非流式意味着服务端必须一口气吐完。

**顺带**：`_wrap_transport_error`（`llm.py:108`）拼的是 `f"请求超时：{exc}"`，而 httpx 超时异常的 `str()` 常为空串，界面上于是显示「timeout：请求超时：」——**冒号后面什么都没有**。

### 2.3 回滚后新建版本，会继承被弃用版本的内容

`agent_service.py:32-36` 取 `latest` 用的是**版本号最大**的那一行，而不是 `agent.current_version_id`。

复现：v1 是正确的预置提示词（306 字）→ 编辑保存成 v2（23 字的测试串）→ 回滚到 v1 → 再新建版本 → **新版本继承了 v2 的内容**（实测：新建的 v3 提示词是 23 字的 v2，而不是当前版本 v1 的 306 字）。

这正是作者最自然的操作路径：*回滚到某个好版本 → 基于它改一改 → 保存*。结果静默拿回废弃版本的内容。打在 D-06 版本化的地基上。

## 3. 交付缺口（spec 承诺 vs 代码实际）

### 3.1 智能体工作室只实现了 1 / 11 个字段

spec §6 要求「角色卡**全字段**编辑（名称、定位、颜色、任务类型、系统提示、绑定模型、参数档、上下文槽位勾选与排序、输出契约、可调用技能、触发方式、启停）」。

`Studio.tsx:93-97` 实际只有一个 `system_prompt` 文本框；`saveVersion`（第 31 行）也只提交它。后端 `VersionCreate`（`schemas.py:51-59`）**接受全部 7 个版本字段**，`_agent_out` 也返回了名称／定位／颜色／启停 —— 是前端没做。更彻底的是：`name / role_label / color / enabled` **连更新接口都不存在**（`agents.py` 只有 GET、版本列表、建版本、回滚）。

这打在**设计立场四「智能体是可调教的工具」**上：作者只能改提示词，改不了上下文槽位与输出契约——而这两项恰是产品差异化的地基（D-09 上下文＝槽位＋预算＋裁剪并明示；§5.5 结构化输出）。

**连带后果（本次实测撞到）**：模型绑定只能写 `model_binding_json`，而工作室**没有任何地方能指定模型**。作者遇到「模型名解析成服务商名字」这种问题时，自己爬不出来。作者已明确要求「项目后期可做到模型与智能体的灵活换绑或编辑」——这条应提到近期待办。

### 3.2 模型名解析会回落到服务商名字

`runtime_service.py:73`：

```python
model = binding.get("model") or settings.get("default_model") or provider.name
```

三个来源全空时（`default_model` 这个键在 `config.py` 里**根本不存在**，全仓只有这一处引用），会把 `provider.name` 当模型 ID 发出去。预置角色卡的 `model_binding_json` 是空的，所以**首次真实运行必然失败**。

### 3.3 故事圣经不可编辑，L1 手动档无路可走

`Architecture.tsx:134-166` 的 logline／主题句／结局方向／幕骨架全是只读 `<p>`，唯一动作是「采纳并写入项目」。spec §1.2 第 6 条与 §6 都写的是「**编辑**故事圣经并确认」。

连带：三档介入里的**手动档**（AI 只看不说）在 L1 没有手工录入入口；§6 的「允许标注杂交方案」（界面只能单选一套）与幕比例编辑也都没有。

### 3.4 服务商只有「增」

spec §6 写「服务商增删改」。UI（`Models.tsx:100-112`）只有添加 + 测试连通性；后端 `PATCH` 与 `DELETE` 都在（实测 DELETE 返回 204 正常）。

### 3.5 连通性测试必然假阳性

`provider_service.py:72` 用 `model=""`（空模型名）发请求；`_sync_probe`（第 90-92 行）**只把 network/timeout 当失败，其余一律吞掉**。任何 400/401/404 都被判为「连接正常」。

所以它验的是**地址可达**，不是**能用**——但界面写的是「连接正常」，读起来就是"能用了"。作者的 Key 是否可用、模型是否存在，它一点没验。本次「测试通过」即为假阳性：真实模型名其实是错的（见 3.2）。

## 4. 存量库迁移缺陷（已处理）

新建项目后，仪表盘的「累计调用／累计费用」**静默显示 0**。根因：

```
sqlite3.OperationalError: no such column: generation_run.parse_error
```

`init_db()` 用 `create_all`，只建缺失的表、不改已有表 —— 就是 `CLAUDE.md` 里记的「无迁移框架」。旧库（建有 `parse_error` 列之前的那一版）的 `generation_run` 少一列，任何查它的接口都 500。

**为什么 P1a 冒烟 19/19 全过却没抓到**：冒烟用 `STORYFORGE_DATA_DIR` 指向**全新临时目录**，那条测试路径**从没验过存量库**。这是比 bug 本身更值得记的一课。

**处理**：旧库（10 表全空，唯一数据是走查时新建的项目）已**改名备份**到 `%LOCALAPPDATA%\StoryForge\backup-stale-p1a\`，未删除；新库重建后与 ORM 结构比对**不符表数 0**，预置 2 智能体 / 25 工具已恢复。

## 7. 模型产出的质量证据

灵感解析（`qwen3.8-flash`，347 + 2720 tokens，44.4s）—— 提示词六条要求逐条照做：

- 主角欲望写成「他/她想要确认那段待销毁记忆中的声音是否真的属于自己…」（要求 2）✓
- 核心冲突源写成两股力量对撞（要求 3）✓
- 参考坐标只写气质相近的作品并附理由：《美丽心灵的永恒阳光》《真探》第一季《银翼杀手》《黑镜》《南方车站的聚会》（要求 4）✓
- 给出 12 条 `open_questions`（要求 5）✓
- 未复述作者原话（要求 6）✓

架构推荐（`qwen3.8-flash`，直连，2392 + 7651 tokens，139.5s）—— 三套方案（七点结构 0.88 / 五幕结构 0.84 / 四幕结构 0.82），每套都：

- 引用解析卡中的**具体字段值**说明适配，不是泛泛而谈（要求 1）✓
- 给出适配度（0–1 小数）、风险、篇幅分配、节奏形态（要求 2）✓
- 写明不适用情形（要求 3）✓
- 给出杂交层，如「主层七点结构，第二幕内部借 Fichtean 曲线」（要求 4）✓
- 结局只作建议并给替代方案，不替作者决定（要求 5）✓
- 完整故事圣经 v0 六项（要求 6）✓
- 信息不足处写「缺什么：」，**不编造设定**（人物一律「（待命名）」）（要求 7）✓

**契约校验 `valid: True`**，三幕比例合计 1.0，五个人物。

## 8. 一处需要留意的记账问题

`completion_tokens` 包含**思维链**。实测一次架构推荐：`completion_tokens: 7651`，其中 `reasoning_tokens: 5435` —— 超过七成是推理，而 `content` 只有 3989 字。

后果：费用记账按 `completion_tokens` 计算会显著高于模型实际"说"的量（各服务商对 reasoning token 的计价规则不同）。当前「模型与费用」页恒显示 `$0`，因为 `model_binding_json` 里没有 `prices`，`compute_cost` 无从计算 —— 费用功能目前是空的。

## 9. 建议的修复顺序

| 优先级 | 事项 | 理由 |
|---|---|---|
| 1 | **提示词 ↔ 契约一致性**：渲染层从 `output_schema` 自动注入键名说明 + 一条跨产物一致性测试 | 不修则结构化输出永远不成立，L2/L3/P2 全都建在它上面 |
| 2 | **超时可配置 + 长任务走流式** | 不修则架构推荐、以及 P2 的正文生成都拿不到结果 |
| 3 | **版本继承取当前版本而非最大版本号**（`agent_service.py:32-36`） | 静默取回废弃内容，直接破坏版本化的可信度 |
| 4 | **模型绑定的界面与外接口**（含 agent 级字段更新） | 作者已明确要求；且它是「1/11 字段」缺口的入口 |
| 5 | **故事圣经可编辑 + L1 手动录入入口** | P1a 验收 §1.2 第 6 条未达成；手动档在三档介入里无路可走 |
| 6 | **迁移框架** | 打包硬前置；本次已实际发作一次 |
| 7 | 连通性测试改为真实验证一次模型可用 | 假阳性会让作者在错误方向上排查 |
| 8 | 第 5 节的九条文案与空态 | 不阻塞，但影响第一印象 |
