## 证据

**1. 建组**（场景卡：目标「把信交给掌柜」/ 冲突「掌柜起疑」/ 转折「信是假的」）

```
group=e07b25e3c71944c7a5622a7bcf1415eb
branch A id=3b60ba52… label=A/B · A
branch B id=0acefaf8… label=A/B · B
```

**2. 两次真实生成**（SSE，先 A 后 B）

```
A: done chars=588
B: done chars=493
```

**3. 两版并存**

```
ab: [('A', True, 554), ('B', True, 473)]   # (side, has_draft, count_words)
```

**4. 采纳 A**

```
adopt chars=554   body == A draft: True
discarded: ['A/B · A', 'A/B · B']
ab after: {'group': None, 'branches': []}
normal branches: []
changes: [..., ('scene','adopt','author','合并分支「A/B · A」（554 字）')]
```

- 正文与 A 的草稿**逐字相同**；两条 A/B 分支都被清掉；普通分支列表里从未出现它们。
- **这次没有 SceneRevision**：该场景原先没有正文，`merge_branch` 只在旧正文非空时才记修订 —— 行为正确，不是缺陷。

**5. 409 守卫**：组还在时再 `POST /scenes/{id}/ab` → **409**；采纳清组后 → 201。

## 已知限制

1. **面板交互未自动化**：勾选、确认框、失败重试只有代码审查；请作者按下面 4 步手点一次。
2. **两次生成是顺序的**：A 完成才跑 B，总等待约 2 倍（SQLite 单写者，避免两条流抢写）。
3. **两版用同一个智能体、同一份上下文**：不支持两版各绑不同模型（那是「模型对比」，另议）。
4. **`side` 由库名解析**：作者手工把 A/B 分支改名成无前缀时，侧别可能标错（采纳功能不受影响）。

## 请作者手点一次（2 分钟）

1. 写作台选一场 → 「A/B 并排生成」→ 等两栏各出一版；
2. 看两栏字数与「差异 N 段」是否合理；
3. 点 A 栏「用这一版」→ 正文应变成 A、修订历史出现「合并分支」、两栏消失；
4. 再点一次「A/B 并排生成」→ 不应报「还有未处理」。
