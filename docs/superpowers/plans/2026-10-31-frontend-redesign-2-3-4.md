## 1. 为什么合并

作者要求「三个批次一起做」。spec §12 原本把剩余页面拆成三个批次（2 设定五页、3 系统四页与阅读器、4 收尾），本计划合并推进，但**保留每批的验证与提交边界**：

- 每页迁移完立即跑构建与测试，并按批提交；
- 批次 2、3 各自出一份截图核对；批次 4 做全站收口；
- 任何一批出现回归，可以只回退该批提交。

## 2. 全局约束

- 不新增 npm 依赖；不引 UI 组件库 / 图标库。
- 后端、数据库零改动；不调用模型。
- 只动 JSX 结构与 `className`；**不动** `useEffect` 依赖、请求顺序、代际令牌、锁定 / 采纳判定、`window.confirm`、`setNotice` 的文案与成败判定。
- 颜色只能取自 `PALETTE`（`src/ui/palette.ts`）对应的 Tailwind 令牌；图表色取自 `ui/chartTokens`；页面里不出现裸十六进制（阅读器主题内部除外，见 §5）。
- 新增的 UI 状态只允许是**纯展示状态**（页签选择、折叠），不改变数据流。
- 每页完成后：该页 `slate-` / `text-xs` 为 0、`LEGACY_DARK` 删一条、`pnpm run build` 干净、`pnpm vitest run` 数字不变（除新增纯模块）。

## 8. 风险

1. **阅读器自铺布局**：它不走外壳内边距，改动只限主题与排版，不碰滚动结构。
2. **工作室 / 模型的页签**：面板内有各自的请求与轮询；页签只切可见性、保持挂载。
3. **纯样式判据**：每页用机械 diff 核对逻辑区；测试数变化即检查是否误动逻辑。
4. **页面较多**：一页一提交，出现回归可单独回退，不必整批回退。
