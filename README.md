# StoryForge · 长篇小说创作台

> 一个跑在作者自己电脑上的长篇小说创作台。把灵感交给可调教的智能体，由它推荐叙事架构、铺开世界观、设计章节，再由作者逐层确认，最后从同一条流水线上产出可阅读、可导出的成品。
>
> **作者始终握着方向盘，AI 负责把方向盘上的每一次转动变成可用的材料。**

---

## 这个项目解决什么问题

常见的 AI 写作工具把「生成」当成终点：给它一个提示词，它吐出一章文字。长篇写作的真实难点不在生成，而在**控制**——

- 写到第 40 万字时，人物性格、世界规则、伏笔进度全都漂了；
- AI 改了一处设定，你不知道这一改会牵动后面多少章；
- 它写得不好的地方你想改，但它已经把你的原文覆盖掉了；
- 你想比较两种写法，但只能覆盖、撤回、再覆盖。

StoryForge 的答案是**五层控制模型**：灵感 → 架构 → 世界观 → 章节 → 正文。上游定义下游，每一层的 AI 产出都只是**待审材料**，作者采纳了才算数。围绕这个骨架，做了四件事：

1. **结构化优先**：人物、势力、规则、时间线、卷章、场景卡都是结构化数据，可查询、可校验、可引用。自由文本只存在于最终正文这一层。
2. **可调教**：每个智能体的提示词、绑定模型、采样参数、能读到哪些上下文、输出什么结构，作者都能看见、能改、能版本化。
3. **控制力**：任何产出都能查到怎么来的、能回退、能被锁住 —— 锁定之后 AI 再也动不了它，但作者照常能改。
4. **本机优先**：稿件、设定、快照、密钥都留在本机；除了调用模型，不联网。

## 功能一览

| 层 | 能力 |
|---|---|
| **L0 灵感** | 一段话 → 结构化解析卡（作者原话永久保留，AI 不得覆盖） |
| **L1 架构** | 2–3 套叙事方案并排对比 → 采纳 → 可编辑的故事圣经 |
| **L2 世界观** | 设定条目 / 规则（硬·软·氛围三级）/ 人物（欲望、恐惧、弧光等八项）/ 关系网 / 时间线 / 术语表 |
| **L3 章节** | 卷 / 章 / 场景卡、章级节奏指标、伏笔表；AI 排卷章与写场景卡，逐条采纳 |
| **L4 正文** | 流式生成 → AI 草稿 → 与旧稿 diff → 采纳 → 修订快照；一致性审计、逻辑自检、状态与伏笔回写 |
| **控制** | 五类对象可锁（含段落锁）、影响面分析、项目快照与回滚、改动历史、场景分支、待复核标记 |
| **成品** | 阅读器（三套主题 / 字号行距 / 整本检索 / 系统 TTS 朗读）、EPUB（两套排版模板 / 封面 / 两级目录）、Markdown、TXT |
| **发行** | pywebview 桌面窗口（WebView2）、单实例、动态端口、PyInstaller 打包、Inno 安装包脚本 |

## 技术栈与架构

```
启动器 (python -m app.desktop)
  ├─ 单实例检查（元数据端口可连性）
  ├─ Uvicorn 127.0.0.1:<系统分配端口>
  │    └─ FastAPI：REST + SSE 流式生成
  │         └─ 同源托管前端产物（不需要 CORS、不需要第二个进程）
  └─ pywebview 窗口（WebView2）→ 加载 http://127.0.0.1:<port>/
```

| 部分 | 选择 |
|---|---|
| 后端 | Python 3.13 · FastAPI · Uvicorn · SQLAlchemy · Pydantic |
| 前端 | React 19 · TypeScript · Vite · Tailwind |
| 数据 | SQLite（WAL）+ FTS5 全文检索 |
| 流式 | SSE |
| 密钥 | Windows DPAPI 加密，界面只回显屏蔽态 |
| 打包 | PyInstaller onedir + Inno Setup |

### 分层约束（有意为之，不是口号）

- `api/` 只做参数校验与调用 service
- `services/` 不碰 HTTP
- `runtime/` **不依赖 FastAPI** —— 智能体运行时能被纯 pytest 覆盖，不需要起服务器

### 智能体运行时

一条固定的链路：

```
槽位收集 → 预算裁剪（裁剪结果对作者明示）→ 提示词渲染
   → 模型调用 → 输出契约校验 → 落库
```

输出契约不是写在提示词里的散落要求，而是**由渲染层从 `output_schema` 自动生成字段说明块**追加到提示词末尾 —— 从机制上消灭「提示词和契约各改各的」这类不一致。

## 工程质量

这个项目最引以为傲的不是功能数量，是**验证纪律**。

| 项 | 数值 |
|---|---|
| 后端测试 | **997 passed**（pytest） |
| 前端测试 | **71 passed**（vitest） |
| 自动化走查脚本 | 每段一个（接口级，0 模型调用） |
| 交付切片 | 20 个，每个都走完「设计 → 计划 → 隔离实施 → 走查 → 独立复查 → 修复 → 合并」 |
| 数据库迁移 | 手写有序步骤 + 版本表，11 条真实迁移在作者库上执行过 |

### 几个具体的工程决定

**迁移永不建表。** 新表归 `create_all`，迁移只做它做不到的事：改已有的表。两套机制职责不重叠，框架因此只有一百多行。迁移语句**冻结为字面量**，不从常量派生 —— 迁移是历史记录，跟着可变常量走会造成「已迁移的库缺列、新装的库有列、测试全绿」的静默分叉。

**失败即拒绝启动。** 半迁移的库比起不来的应用危险得多。迁移每步一个事务，失败不记为已执行。

**一个口径只定义一次。** 比如「章内正文怎么拼」曾经在四个导出路径里各写一遍，在 P5 收敛成 `_chapter_text` 一处；「未回收伏笔」从三处各写一遍收敛成 `is_unrecovered` 一处。这个项目被「第二份清单」坑过好几次，所以把它当成硬约束。

**契约校验器放过可选字段的 `null`。** 模型把可选字段写成 `null`（「这项为空」的常见写法）原本会让整份 payload 校验失败、降级纯文本。可选字段的 `null` 是省略的另一种写法，必填字段的 `null` 是真空缺 —— 两者不该一视同仁。

**用真实用户动作验证交互。** 曾经把「重选下拉即可更新」当成通过，复查指出：下拉的当前值就是那个选项，原生 select 重选同一个 option **不触发 change 事件**，那条路径根本走不到 —— 我的「验证」是合成事件，是假验证。改成按钮并真鼠标点击复验。

## 跑起来

```bash
# 后端
cd backend
uv sync
uv run python -m app.desktop      # 桌面窗口（推荐）

# 或者只起服务，用浏览器
uv run uvicorn app.main:app --port 8756

# 前端（开发期热更新）
cd frontend
pnpm install
pnpm dev                          # 5173，/api 代理到 8756
```

**需要配一个模型服务商**（OpenAI 兼容即可，可接本地 Ollama / LM Studio）才能体验 AI 功能。没有模型也能完整走通手工路径：建项目、写设定、排章节、写正文、阅读、导出。

### 测试

```bash
cd backend && uv run pytest      # 997 passed
cd frontend && pnpm test         # 71 passed
cd frontend && pnpm build
```

### 打包

```powershell
powershell -ExecutionPolicy Bypass -File scripts/build.ps1
```

产物 `backend/dist/StoryForge/StoryForge.exe`。安装包需要 Inno Setup 6.3+，见 `packaging/README.md`。

## 数据在哪

**永远不在程序目录里。**

| 东西 | 位置 |
|---|---|
| 数据库 | `%LOCALAPPDATA%\StoryForge\storyforge.db` |
| 密钥 | `%LOCALAPPDATA%\StoryForge\secrets.bin`（DPAPI 加密） |
| 设置 | `%LOCALAPPDATA%\StoryForge\settings.json` |
| 项目资产（封面等） | `%LOCALAPPDATA%\StoryForge\projects\<项目 id>\` |

程序本体只读，可以装在 `Program Files`；卸载不会删掉书稿。开发期可用 `STORYFORGE_DATA_DIR` 覆盖。

## 没做完的部分（如实记录）

- **逻辑自检的图形化视图**（因果链图、设定投放曲线、性格漂移曲线）—— 按产品决策 D-22 推到二期

- **阅读器分页模式、跨章自动续读**未做
- **只支持 Windows x64** —— DPAPI、WebView2、Inno 都是 Windows 的东西
